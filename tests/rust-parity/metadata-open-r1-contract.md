# Controlled metadata initialization

This is a minimal additional initialization API returning the existing `Metadata` type, plus a consuming `close(self) -> Result<()>`. It is intended for callers that already carry an `OperationControl`, including remote cache consumers. It does not rewire consumers or change the existing `Metadata::open` implementation.

- `open_controlled(home, write, control)` checks the original control before all workspace/filesystem work. It uses the exact caller deadline throughout; it does not create a fresh five-second budget.
- Writable controlled opens use the fixed Go schema lease namespace through the already frozen historical writer helper. Read-only opens neither acquire/create that lock nor initialize a missing or version-zero database.
- Opened SQLite connections use zero busy timeout. The existing `checked_sql` loop retries actual BUSY/LOCKED with bounded sleeps and the original control. Its existing terminal-error branch gains one stop recheck, ensuring an elapsed absolute cutoff cannot outrun the preceding control check.
- Initialization retains the old `open` schema and diagnostics, including `vault.record_missing` (exit 3), `vault.schema_newer` (exit 4), `vault.schema_invalid` (exit 4), `IF NOT EXISTS`, and synchronous FULL for writers. The existing acceptance of negative versions and nonempty version-zero databases is explicitly preserved. This API does not claim to replace the stricter fixed-Go historical migration boundary or to add its WAL/deleted-generations behavior.
- Schema initialization is a BEGIN IMMEDIATE transaction with individually checked CREATE TABLE, user_version, and COMMIT statements. Failure before committed success performs one explicit nonblocking rollback when a transaction remains active. Its failure is retained, Drop rollback is disarmed, and the connection is explicitly closed. If SQLite has already auto-rolled back, no invented second rollback error is added.
- Setup, schema-lease close, final control checks, and connection close retain primary and cleanup ToolkitErrors through the exact historical `finish_historical` convention. Success after COMMIT can race cancellation: the returned error closes resources but does not claim already committed initialization was undone. No public Metadata statements or transactions escape, so consuming close has no borrower to invalidate. An unsuccessful rusqlite close retains its error and follows the existing historical fallback Drop behavior for the returned connection; actual close failure is not claimed tested.
- Control bounds lock waits and checks statement boundaries. It does not make a synchronous filesystem syscall or an individual SQLite statement preemptible. Later Metadata methods retain their existing contracts; `open_controlled` does not make unqualified `read`/`put` cancellable or change their post-operation timeout restoration.

## Verification limits

Twelve new Rust tests are declared, all NOT_RUN. Fixtures exercise actual SQLite EXCLUSIVE/RESERVED/shared-read contention at version read, BEGIN and COMMIT, using a bounded scoped cancellation thread only after the busy callback observes real contention. Deadline tests reuse the original deadline. Fixtures own a unique root, join all threads, explicitly close healthy connections, and remove their own root; failed setup/panic remains bounded by scope and RAII. Separate tests cover old/new diagnostics, read-only no-initialization/write rejection, SQL initialization error rollback/recovery, concurrent open/lease release, and nested typed-error composition. Error composition is an injected model, not an OS/SQLite close-failure execution claim.

The approved Linux pure runner supports selected production modules and binding-contracts only, with no SQLite/core target. No Cargo, cache adoption, process lease, game, release, push or main-tree modification is performed for this stage. Rustfmt parsing, exact-byte comparisons and patch/hash checks do not establish compilation, Windows execution, performance or full Go parity.
