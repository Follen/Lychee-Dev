# AGENTS.md

Guidance for agents working in this repository.

## What this project is

Lychee Dev is a lightweight graphical World of Warcraft data inspection addon plus
the tooling that drives it. There are three deliverables in one repo:

| Path | Deliverable |
| --- | --- |
| `add-on/` | The installable addon, its tests, tools and technical documentation. |
| `Lychee Dev skill/` | The versioned source of the `lycheedev` agent skill. Copies installed into `~/.agents/skills/lycheedev` come from here. |
| `packages/cli/` | The published npm package `lycheedev`: installer, doctor and automation CLI. |

The addon's primary workflow is: paste agent-generated `/run` or `/script` Lua into
`/dev`, execute it explicitly, inspect the result, and select the result text for
copying. SavedVariables keep a bounded history of recent runs so nothing grows
without limit.

Use [EllesmereUI](https://github.com/EllesmereGaming/EllesmereUI) as the reference
for engineering discipline, module boundaries, UI consistency, taint avoidance and
performance. It is a reference, not a runtime dependency. Do not copy its branding,
product names, media or implementation wholesale; adapt the principles to this
addon's architecture and naming.

## Repository layout

- Runtime paths below are relative to `add-on/` unless stated otherwise.
- Root `README.md` and `README_zhCN.md` describe installation and the combined
  addon and skill workflow.
- `packages/cli/vendor/` is generated by `packages/cli/scripts/vendor.mjs` and is
  not edited by hand.

Commands, from the repository root:

```powershell
# full four-client test matrix
powershell -NoProfile -ExecutionPolicy Bypass -File add-on/tests/TestAll.ps1

# release ZIP (must contain "Lychee Dev/", not "add-on/")
powershell -NoProfile -ExecutionPolicy Bypass -File add-on/tools/Package.ps1

# npm package: stage the payload, then test and pack
cd packages/cli
node scripts/vendor.mjs
node scripts/selftest.mjs
npm pack --dry-run
```

The ZIP must contain `Lychee Dev/`. Tests, tools, docs, skills and investigation
data are excluded from both the ZIP and the npm payload.

| Retail Midnight `12.1.0` | `120100` | `Lychee Dev_Mainline.toc` | `_retail_` |
| Classic `5.5.4` | `50504` | `Lychee Dev_Mists.toc` | `_classic_` |
| Classic Titan `3.80.2` | `38002` | `Lychee Dev_Wrath.toc` | `_classic_titan_` |
| WoW: Forever `1.60.1` | `16001` | `Lychee Dev_Forever.toc` | `_classic_beta_` (see below) |

- Do not add Classic Era, Anniversary, PTR, Beta or older expansion branches unless
  the project owner changes the product scope. `_classic_era_`, `_anniversary_` and
  `_beta_` may be present on a machine but the addon does not install into them.
- Each TOC loads exactly one file from `Core/Clients/`, then `Core/Compatibility.lua`,
  its matching generated event catalog, and the same shared module list in the same
  order.
- Treat all four TOCs as release sources of truth. When a supported client changes,
  update its TOC, client profile, this table, both READMEs and the build tests together.
- **A client folder is a location, not an identity.** The launcher reuses a test
  folder for whatever is on the test track, so WoW: Forever currently ships in
  `_classic_beta_` on that track while a dedicated `_forever_` folder is also
  accepted. Never decide a build from the folder name alone: read the client's own
  `.flavor.info` product code (`wow_forever`, `wow_classic_titan`, ...) and
  `version.txt` build, and only fall back to the folder. `_classic_beta_` carrying
  `5.5.x` is the MoP classic test track, not Forever. Both the CLI (`wow.js`
  `resolveProduct`/`flavorForClient`, `src/py/instances.py`) and any new tooling must
  follow this order.

## Non-negotiable acceptance criteria

1. **Zero cost while disabled.** An opt-in feature creates no frames, registers no
   events, runs no hooks and performs no polling until it is enabled. Build lazily on
   first enable and stop owned work when disabled.
2. **Zero behavior change without opt-in.** New user-facing features default to off.
   Only a narrowly scoped bug fix may change existing behavior without opt-in.
3. **Low cost while enabled.** Prefer events and callbacks. Do not use `OnUpdate`
   polling or wall-clock timers as state or logic gates. Avoid allocations, repeated
   scans, redundant writes and unbounded loops in hot paths.
4. **Zero taint risk.** Protected UI and Blizzard-owned objects are trust boundaries.
   A feature that cannot be made combat-safe and taint-safe must not ship.
5. **One shared API surface.** Verified client differences live in
   `Core/Compatibility.lua` or the selected client profile. Do not scatter product
   checks or speculative legacy fallbacks through feature modules.

## Lua and file organization

- Use the WoW Lua 5.1 subset. No `goto`, labels or syntax the live client rejects.
- Keep ordinary Lua source, comments, identifiers and user-facing English strings
  ASCII. Locale data files may contain UTF-8 and must be UTF-8 without BOM.
- Start modules with `local ADDON_NAME, ns = ...` when a shared namespace is needed.
  Keep state local or under `ns`; create globals only for declared SavedVariables or
  a deliberate public API.
- Keep `.toc` load order explicit: compatibility gate, libraries, database and
  migrations, shared core, runtime features, then optional UI.
- Put distinct features in distinct modules. Do not mix runtime behavior, options UI,
  migrations, localization and reusable widgets in one catch-all file.
- Keep heavy, infrequently used UI lazy or LoadOnDemand where the structure allows.
- Reuse the shared widget, styling, tooltip, popup, media and layout helpers. Do not
  create a second visual system for one feature.
- Comment only for non-obvious invariants, API hazards, ownership, combat
  restrictions, performance decisions or migration rationale.

## Lifecycle and SavedVariables

- SavedVariables are not reliable at Lua file scope. Read, initialize or migrate them
  only after the owning addon's `ADDON_LOADED` event.
- Defaults fill missing keys without overwriting user values. Do not persist values
  that merely duplicate defaults when the database layer can prune them.
- Every migration is versioned, idempotent, ordered before feature initialization and
  safe to run repeatedly. Preserve unknown and newer data.
- Never cache a profile table across profile switches or database re-rooting. Fetch
  the current profile at use time.
- Disabling a feature must unregister its events, cancel its owned timers, release or
  hide its transient UI, and leave no active hook work beyond a constant-time guard.

## Events, hooks, combat and taint

- Use `HookScript` or `hooksecurefunc` for Blizzard-owned frames and functions. Never
  replace their scripts with `SetScript`.
- Do not write custom fields onto Blizzard-owned frame tables. Keep addon state in
  external weak-key tables when it must be keyed by a Blizzard object.
- Do not hide, reparent, rename or mutate protected frames during combat. Guard with
  `InCombatLockdown()` and defer protected work to `PLAYER_REGEN_ENABLED`.
- Prefer addon-owned secure frames and documented secure templates or state drivers
  when secure behavior is required. Keep insecure configuration out of restricted paths.
- On every supported client, check `issecretvalue` before comparing, formatting,
  indexing with or branching on values that may become secret in combat. Fail open to
  a harmless visible state rather than throwing or leaving stale hidden state.
- Event handlers filter early by event arguments or unit, do no work while the feature
  is disabled, and unregister one-shot events immediately after use.
- A timer may debounce presentation work or defer to the next frame. It must not
  replace a real game event or become a perpetual polling loop.

## UI and localization

- Follow the existing spacing, typography, colors, borders, control sizes and
  interaction patterns. Find the nearest existing component and match its structure
  before creating anything new.
- Prefer project-owned tooltip and confirmation helpers for plain addon UI. Use
  `GameTooltip` directly only for native item, spell, unit or hyperlink content.
- Keep layouts stable: controls must not resize or shift when labels, values, hover
  states or dynamic content change. Check long localized strings at representative scales.
- Translate at the rendering boundary. Keep internal identifiers, routing keys,
  profile keys and search identities stable and language-independent.
- Preserve positional placeholders such as `%1$s` and `%2$d`. Missing translations
  must fall back safely to the source string.
- Both locale tables must stay in lockstep; `LocaleTests` compares key counts and
  placeholder sets, so add a key to `Core/Locale.lua` and `Core/Locale_enUS.lua` together.
- Visual changes need before/after screenshots and in-game inspection on a supported build.

## Performance rules

- Keep disabled fast paths first and constant time.
- Prefer memoized state changes over rewriting the same texture, alpha, text, point or
  attribute on every event.
- Avoid per-frame table and function creation, full-table scans and repeated API calls
  in combat or high-frequency events. Cache immutable lookups and invalidate derived
  caches from concrete events.
- Use local aliases in genuinely hot paths only when profiling justifies them.
- Reuse persistent event drivers where ownership is clear. Do not create disposable
  event frames or unbounded tickers.

## The npm package and CLI

`packages/cli` publishes `lycheedev` (lowercase; npm rejects uppercase names). It ships
a vendored copy of the addon and the skill so a single install needs no repository
checkout.

Design rules:

- The package declares **no runtime npm dependencies**. Keep it that way.
- The CLI is a thin wrapper. It owns installation, detection and `doctor`; everything
  that touches the game or SavedVariables is delegated to the bundled
  `automation.py`, so that logic exists once.
- `packages/cli/vendor/` is generated. Run `node scripts/vendor.mjs` after changing
  add-on or skill sources. It refuses to vendor a task registry that contains local
  task blocks.
- Python dependencies install into `~/.lycheedev/python` via `pip --target` and are
  reached through `PYTHONPATH`. Never install into the user's site-packages.
- Config lives in `~/.lycheedev/config.json`; the installed skill lives in
  `~/.agents/skills/lycheedev`.
- Keep `node scripts/selftest.mjs` passing. It checks the packaged payload, the TOC
  file lists, the empty registry and the CLI surface without network or game access.

## Release process

Version numbers: the addon TOC `## Version:` and `packages/cli/package.json` `version`
are released together and the git tag must match the npm version.

```powershell
# 1. verify
powershell -NoProfile -ExecutionPolicy Bypass -File add-on/tests/TestAll.ps1
cd packages/cli; node scripts/vendor.mjs; node scripts/selftest.mjs

# 2. bump and tag
npm version 0.8.1 --no-git-tag-version     # then update the TOC version(s)
git commit -am "release: 0.8.1"
git tag v0.8.1

# 3. publish (CI does this on the tag; locally needs an OTP)
git push --follow-tags
```

Publishing on tags is handled by `.github/workflows/publish-npm.yml`, which verifies
on Windows and Linux, runs the addon matrix, re-checks the tag against
`package.json`, and publishes with provenance. See the README for the one-time
`NPM_TOKEN` configuration.

Never publish a registry that contains task blocks, and never commit
`packages/cli/vendor/` or a packed `.tgz`.

## Change and verification workflow

- Make one focused behavioral change at a time. Do not mix feature work with
  unrelated cleanup or formatting churn.
- Before editing, inspect the relevant `.toc`, initialization path, database
  defaults and migrations, the module entry point, and the nearest equivalent feature.
- For API or compatibility work, verify names and behavior against the exact
  baselines above. Do not rely on memory or a latest-branch assumption.
- At minimum review the diff, confirm every referenced file is listed in the correct
  TOC order, and run the relevant lint, syntax, test and packaging commands.
- Test both disabled and enabled. For stateful changes also test `/reload`,
  logout/login persistence, profile switching, first install, upgrade from prior data,
  and reset-to-default.
- For protected UI or combat-sensitive work, test entering and leaving combat with Lua
  errors enabled and confirm there are no blocked actions, forbidden calls or taint.
- Record the exact client version and Interface used for in-game testing. Never claim
  in-game verification when only static checks ran.
- Any visual change needs before/after evidence. Any localization key change must keep
  both locale tables in step.

## Final review checklist

- New settings default off and disabled features have no runtime machinery.
- Enabled behavior is event-driven, bounded and allocation-conscious.
- No Blizzard-owned scripts or frame tables are overwritten.
- Combat lockdown and secret values are handled before unsafe operations.
- SavedVariables initialization and migrations preserve user data.
- Lua stays 5.1-compatible and TOC order is correct.
- Retail `120100`, Classic `50504`, Titan `38002` and Forever `16001` each select the
  matching profile and event catalog, share the same ordered implementation, and pass
  the whole matrix.
- The npm payload vendors cleanly, ships an empty task registry, and its selftest passes.
- Reported verification matches what was actually run.
