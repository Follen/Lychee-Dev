Date: 2026-09-28. Scope: design review, not implementation acceptance. Reviewed the proposal, current journal resource ownership/admission structure, and the prior memory/slot experiment boundaries. No new live input was sent for this audit.

Companion acceptance specifications: [installation-to-release tests](live-memory-slot-tests.md) and [activity/reload UI](live-memory-slot-ui.md). The table below preserves the initial design audit; its pending/not_run labels describe that review point. Subsequent implementation, fixes and scoped Retail acceptance are recorded in the [current implementation record](live-memory-slot-implementation-2026-09-28.md). Native/public CLI execution, runtime-loss recovery, capacity rollover, immutable history, managed removal and UI evidence now exist; two simultaneous clients, other accepted builds, complete ledger loss, generation binding and legacy transport retirement remain separate open gates.

Verdict: the direction is viable, but the previous proposal was not yet a closed protocol. Recovery rules alone do not prove bootstrap freshness, exclusive ownership, slot availability or automatic progress. The updated proposal records the corrections below; unresolved gates must be prototyped before production replacement.

## Additional invariants

- **Continuation under a stated fault model:** after a finite number of reloads and once the intended target, disk and memory access become available, replay-safe/resumable fixtures must reach completion without manual journal edits. Unlimited user interference cannot have a guaranteed finite completion time. Pending observations are not terminal failures, but exhausted deadlines must not spin forever.
- **Runtime generation is not the connection:** a logical owner may reconnect after reload without creating a second connection. A new runtime must not inherit prior execution authority or loaded-slot assumptions. Process replacement is a new instance and needs explicit target resolution under the task's constraints.
- **Data and execution:** slot source must be a generated data-only wrapper. Business code remains encoded data until the main addon has checked actor/runtime/connection/fence/slot/hash and accepted the exact commit. Lua file evaluation itself must never run the probe before validation.
- **Check/apply race:** workflow checks return bound evidence (subject identity, relevant state/version, observation time). Revalidate dispatch prerequisites on the addon side; do not operate on whichever target happens to be selected later. Idempotency is part of the step contract, not inferred by the agent from a successful prior call.
- **Semantic interruption:** repeating an observation after reload is a new observation with an explicit gap. It cannot recover a missed event or recreate a transient scene that no longer exists. A workflow may continue with that gap only when its task semantics permit it.
- **User opt-out:** disabling the bridge is an explicit user action, not a transient disconnection that automatic recovery may immediately undo. Retain evidence and report waiting/disabled. Closing the indicator alone has no business effect.
- **Maintenance:** addon updates and the 64-slot manifest require installation maintenance admission across all instances sharing that installation. Do not update files under accepted or unresolved work. Lock acquisition must follow one ordering; maintenance waiting cannot hold a journal transaction or deadlock with a driver waiting to release a result.
- **Capability loss:** unavailable process-read permission, unsupported runtime protocol or inconsistent addon files is a typed capability/state error. No hidden QR fallback, arbitrary chat execution or implicit privilege escalation.
- **Deletion/corruption:** `.lycheedev` improves CLI-crash recovery, not survival of deliberate deletion. The host index may locate known operation metadata but is not a secretly complete second journal. If both durable outputs and runtime evidence disappear, automatic continuation requires a domain check or replay-safe step; otherwise the exact unresolved effect must be surfaced.

## Keep the implementation small

One coordinator exposes execute/status/resume and owns the sole transition reducer. Four internal responsibilities suffice: durable operation/connection records; resource arbitration; managed slot publication; native memory observation. Reuse delivery for installation and desktop for input/WGC. The cache is a bounded hint collection inside that reader, not a fifth state machine. Separate adapters allow deterministic fault injection. The Skill selects target/project, probe semantics and budget, then drives the coordinator's structured next action; it does not implement another state machine or delegate memory work to wowdump.

Every irreversible boundary needs both an invariant and a failing-before/fixed-after fixture. Begin with a deterministic fake game/filesystem/input driver to enumerate reordered events and crashes. Then prove startup freshness, shared-installation slot routing and control-capacity admission in a dedicated real-client lab. Broad implementation or QR removal before those three gates would lock the project into unproven assumptions.

Acceptance evidence must distinguish design correction, offline proof, single-client experiment and multi-client real acceptance. This audit does not mark any new transport gate passed.
