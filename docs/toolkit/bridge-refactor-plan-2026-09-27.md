# Lychee Dev 桥接与界面重构总方案

日期：2026-09-27。状态：原始实施方案；下方实施追踪记录本轮工作区进度，不代表完整客户端验收。历史调查结论保留。

## 实施追踪（2026-09-27）

独立 Retail 后台 PostMessage 回显实验已两次通过，证据见
[键盘实验验收](../../tests/bridge-input/acceptance-2026-09-27.md)。它验证了所选窗口的唤醒、分段输入、接收、重复提交封存与清屏，不等于生产桥、其他布局或 Classic/Titan 验收。

当前工作区把生产输入改为 `LDB1` stage → 物理提交 → `receiver_commit_ready`
challenge → 精确匹配 nonce、attempt、challenge、正文摘要的 `LDC1` commit；旧提交键本身不能执行新 stage。CLI 已接入 `live probe load --budget-seconds <1-120>`，在不可变请求中保存预算；首连输入采用持久 `BTP-...` attempt，`live status`/`live resume` 可观察原尝试且不重复未知输入。以上是代码合同，最终自动检查与生产真机结果另记于
[实施状态](implementation-status.md)和[回归矩阵](regression.md)。独立兜底重载与 UI 已有工作区实现，生产真机与视觉验收仍标为待验。

工作区还提供接收器绑定配置：设置页和 `/dev receiver bind <wake|submit|close> <chord>` 修改插件自己的运行时 override，`/dev receiver reset` 恢复默认值。只接受 `ALT-CTRL-`、可选 `SHIFT-` 加 `[`, `]` 或 `F1`..`F12`；close 的末端按键须与 wake、submit 都不同。遇到已有绑定冲突或 override 未生效时拒绝配置，不执行 `SaveBindings` 改写玩家账号绑定。首连可用 `--wake-binding <chord>` 指定已知自定义唤醒键，ready 回执返回三项实际生效值供 CLI 核对并保存；不猜键。生产客户端与跨布局验收仍待进行。

`live status`/`live resume` 接受 BTP 与 OP。`live abandon` 在用户明确决定后也可处理未决 BTP 和固定兜底 reload OP，保留未知效果并释放宿主所有权，不发送游戏输入、也不声称已撤销效果。

本轮最终快捷键为 Ctrl+Alt+] 唤醒、Ctrl+Alt+Shift+] 提交、Ctrl+Alt+[ 关闭。
下文早期讨论中的 Shift+[ 提交和“紧急解锁键未定”由此修订；关闭只释放接收器，不表示业务取消或 ACK。

### 本次讨论确认的范围

- 接收窗口是插件自带的机器命令入口，类似专供桥使用的聊天框；唤醒不依赖已连接的桥，首次 identify/connect 也在这里完成。
- 二维码只承担身份、握手、状态、摘要和最小错误回执；完整业务报告统一走 SavedVariables（SV）。本轮不建设无 reload 短脚本上传和完整光学结果通道。
- Agent 按实验选择执行预算，CLI 与插件共同校验并执行；输入接收的硬期限独立，不能随探针预算延长锁住玩家。
- 正式接入生产桥之前，先写独立测试插件和宿主测试脚本验证输入与重载能力。
- CLI 封装传输、恢复和清理，skill 负责研究、探针设计、预算和结果判断。
- 增加不依赖桥或 session 的兜底重载：固定 `Esc × 3 → Enter → /reload → Enter`，用于安装激活及桥失联恢复。以下各节以这些决定为准。

## 1. 要解决什么

让 CLI 能独立完成连接、命令接收、执行、结果核验和清理，正常流程及可恢复异常不依赖 Computer Use。玩家误触时宁可明确拒绝本次输入，也不能执行被污染的命令；发生未知执行状态时不能盲目重放。

聊天框作为机器命令入口不可靠，是需要替换的核心环节，但不是全部根因。现有证据还确认了三类独立问题：插件允许最长 120 秒异步执行，而宿主部分观察只有 15 秒；普通 EditBox 的焦点门禁与聊天专用恢复事件不匹配；报告编码失败未可靠生成机器可读失败回执。超时与用户取消也存在混淆。仅增加 Esc 或换输入框不能解决这些问题。

保留现有窗口/进程/角色核对、受管安装校验、操作所有权、不可变队列、报告核验和持久化证据链。旧版的恢复能力按新合同补齐，不恢复旧 Python 实现或导入旧用户数据。

## 2. 总体结构

### Skill 编排：根据对应 build 的源码自主构建探针

用户明确要求通用探针编排，不将能力限定为 UI 或固定测试模板。Skill 应从问题出发，查询当前已核验客户端 product/build 对应的固定 source/API 文档，结合目标插件版本源码，主动选择可调用接口、事件、状态和实验方式，生成有界 Lua 探针。没有现成脚本不是停止或改用 Computer Use 的理由。

通用流程是“问题与假设 → 固定版本、研究定义及调用点 → 设计最小可判别实验 → 执行并读取证据 → 按结果调整假设/探针 → 清理交付”。API、对象名、动作顺序、采样字段、预算和断言由任务与源码决定，不写死在 skill；示例不是允许动作的白名单。覆盖状态调查、事件时序、对象生命周期、业务回归、错误诊断、性能采样以及 UI 等场景。

SourcePin 必须记录精确 commit 及其与客户端 build 的对应证据；不能把 live 分支或最新源码当成匹配版本。精确来源缺失时明确差距，在已有授权内可用最小能力探针核对实际行为。研究参数、返回值、事件时序和调用前提后积极组合实验；不凭记忆猜接口，也不因静态分析尚未证明就一概停止运行时调查。

实现时在 SKILL.md 增加通用编排入口，并衔接现有 source research、live investigation、错误及性能 references。Skill 固定方法、证据和生命周期要求，保留 agent 按源码构建探针的自由度；更换实验要使用新 revision/request，原操作未决先恢复。保护操作、secret 值和不可回滚副作用遵守实际 API 与任务授权。

CLI 对外提供完整调查流程，内部处理唤醒、nonce、staged 摘要核对、提交、有限重传、报告持久化与核验、ACK/finish；保留已有原子 run/ack/finish 语义供明确需要分步控制的任务使用。Agent 不逐字符编排传输，也不因看到二维码、accepted 或已加载就结束任务。能力未实现前不在 skill 或命令目录宣称已支持。

#### 示例：本次 UI 回归如何运用该方法

用户进一步明确：普通插件 UI 调试应充分使用 `/run` 同等的 Lua 能力。这里的重点是编写能完成任务的脚本，而不是增加聊天命令或反复操作鼠标。代码经现有受管探针运行；是否需要替换传输通道与探针是否正确是两个问题。

以下是本次 UI 故障可采用的步骤，不是其他探针必须套用的固定流程：

1. **前置检查**：确认当前 runtime、非战斗条件、目标插件与接口可用；声明需要的用户数据或测试夹具。只读现场检查不暗中创建或保存个人方案。
2. **准备场景**：在 load 完成之后主动打开插件、切换标签、进入编辑页、展开选择器；不依赖重载前的临时面板或 Frame 引用。
3. **执行动作**：优先调用目标插件已有控制器方法或组件接口。必要时调用其自有按钮/滚轮脚本，按实际签名传入参数；滚动检查使用实际滚动方法或偏移 setter，而不是只读取坐标就结束。直接改偏移只覆盖布局，调用滚轮处理器才覆盖该处理器的路由逻辑，两者要标明。
4. **断言效果**：记录动作前后内外滚动偏移、可见条目和选择身份。对内部滚动断言内层按预期改变、外层不变；覆盖首尾边界、展开/收起、外层滚动、分类切换和复用格子。仅输出 passed=true 或一份几何快照不算回归。
5. **清理与报告**：注册有界清理，取消定时器、清理自己创建的测试资源；记录执行过和未执行的断言。预期失败使用明确失败状态，不把捕获到的异常包装成普通成功。等待采用可观测条件、事件或有界回调，避免堆叠固定长延时。

鼠标相关能力按验证目标划分：程序调用可以覆盖普通自有 UI 的打开、回调逻辑和滚动结果；真实鼠标命中、遮挡、焦点与游戏原生事件分派不能仅靠手调回调证明。依赖 GetCursorPosition 的路由，需要在当前真实位置采样，或通过目标插件可测试的局部接口传入坐标；不能覆盖全局鼠标 API 后声称真机输入已通过。受保护操作继续遵守硬件事件与战斗边界。

实施优先补充 skill 的通用 source → probe → evidence 编排，再决定哪些确实需要新增 CLI 能力。普通业务回归不以新增“保留现场诊断通道”为前置条件；该能力只解决必须观察重载前现场的独立需求。

### 短回执与完整 SV 报告

经当前实现核对：CLI 将不可变探针写入受管 `Bridge/Definitions.lua` 队列，经 prepare/reload 加载，再 load/run；插件生成报告与二维码状态回执，经 flush/reload 将完整报告落入 SavedVariables，CLI 读取并核验，最后 ACK/finish 确认与清屏。正常新探针链路包含加载、报告持久化两次 reload；当前原子 ACK 不再增加第三次清理 reload。文件名不是旧版 automation.lua，二维码状态回执也不代替完整 SV 报告。

本次决定采用单一的完整报告通路。身份、接收就绪、staged/accepted、运行状态、报告摘要、最小错误、ACK 和清屏仍通过短回执传递；日志、采样、断言与业务结果正文写入 SV。无需为完整结果另建光学分帧、短脚本上传及两套恢复协议。

| 路径 | 当前证据与目标 |
|---|---|
| 已持久化报告恢复 | 当前 execute_probe.go 优先读取精确报告，再决定是否等待重入二维码；reconcile_report.go 可在没有运行客户端或捕获流时核验该操作已保存的报告。保留此能力，不重复发 flush/reload |
| 已完成操作确认 | 当前原子 ACK 不增加清理 reload；已完成 finish 按既有合同复用归档清理证据，不能增加不必要输入 |
| 业务探针与完整报告 | 统一使用 Definitions.lua、必要的加载 reload、运行、报告持久化 reload、SV 核验流程 |
| 无 reload 的通用短探针与完整结果回传 | 不在本轮实施范围；不得在 CLI 或 skill 宣称已支持 |

SV 在本方案中不是即时写盘接口：报告先进入插件内存，当前 CLI 完整取回仍依赖 flush/reload。加载新探针也可能重载。应先完成采样、断言和探针自身清理，再持久化这份结果；不能在采样中途为读报告破坏场景。新探针需要重建 UI 时，在加载重载之后准备场景。

报告超限、编码失败或回执丢失时保留同一个操作，通过最小失败回执、精确查询或已有报告恢复推进；禁止重跑脚本以获得另一份结果。已落盘的精确报告直接核验，已完成的 finish 复用归档证据，不重复 reload 或输入。

Skill 必须判断任务依赖原现场还是可重建场景。如果现有已加载能力不能在首次重载前采到原现场，明确这一限制；不能悄悄重载后声称观察了原现场，也不为此临时引入任意 Lua 上传入口。

```text
CLI：取得窗口所有权 → 唤醒 → 核验 ready → 发送短报文
                                             ↓
插件接收器：焦点确认 → 严格解析 → staged 冻结与摘要回执
                                             ↓
CLI：读回并比较摘要 → 专用物理提交键
                                             ↓
插件：发布 commit_ready challenge → CLI 发送精确 LDC1
                                             ↓
插件：核验 nonce/attempt/challenge/正文摘要 → accepted → 现有业务分发器
                                             ↓
探针：定义队列 → reload 加载 → run → 报告回执
                                             ↓
结果：reload 落盘 → 读取 SV 并核验 → ACK / finish → display cleared
```

左上角二维码继续承担机器回执展示，CLI 通过既有 WGC 捕获与解码读取。输入框只传短小的协议动作，不粘贴完整 Lua 探针；探针仍由受管队列加载。工作台、接收器和二维码彼此独立，输入框消失不能带走报告。

## 3. 快捷键与接收窗口

| 动作 | 方案 |
|---|---|
| 唤醒 | 默认 Ctrl+Alt+]，规范键名 `ALT-CTRL-]` |
| 提交 | Ctrl+Alt+Shift+]，规范键名 `ALT-CTRL-SHIFT-]` |
| 普通 Enter / Esc / Tab | 接收期间吞掉，不提交、不关闭、不传播到角色操作 |
| 鼠标点击 / 滚轮 | 接收期间由自有模态层拦截，不触发下面的界面 |
| 关闭接收器 | Ctrl+Alt+[，规范键名 `ALT-CTRL-[`；释放本次输入，不替代业务取消或 ACK |
| 超时 | 不可续期的硬截止；到期释放焦点、绑定和模态拦截 |

基础唤醒入口随插件加载可用，不依赖 bridgeEnabled、session 或已打开的工作台。首次安装、尚未连接、disconnect 后都能直接唤醒；identify/connect 在同一窗口提交。唤醒只打开接收器，不自动授予探针执行权限；未连接时仅允许身份、连接和满足各自前提的恢复动作。完全禁用或未加载插件时入口不存在，安装激活使用第 5 节的兜底重载。

基础入口优先使用静态绑定声明和最小处理器，不提前创建接收窗口或启用调查订阅。必要的基础注册成本单独测量，不再把“桥未连接”解释为“无法唤醒”。不覆盖玩家已有绑定，不自动保存整套账号键位。唤醒为幂等 open，重复唤醒不关闭窗口、不清空报文、不延长截止时间。接收框持有焦点时也必须能识别专用组合键。

接收框默认取得焦点，但不永久抢焦点。失焦、战斗、离开世界或人工解锁立即终止接收；不自动与玩家争夺控制。插件层的短时模态无法保证屏蔽操作系统快捷键、全部保护界面或其他插件，不能把罕见快捷键描述成 agent 专属权限。

**能力门槛：** 固定正式服源码支持多修饰键绑定形式；独立 Retail 后台 PostMessage 回显实验已两次通过唤醒、接收和清屏，见[实验验收](../../tests/bridge-input/acceptance-2026-09-27.md)。该实验不证明生产桥、其他键盘布局或 Classic/Titan 的投递；这些仍需单独验收。若后台路径不成立，不能静默回退聊天输入或 Computer Use。

## 4. 抗玩家干扰与重试

报文包含版本、receiver nonce、runtime epoch 的关联信息、operation/request ID、attempt ID、动作、参数、长度和校验。只允许已声明动作；字符集受限、容量有上限。完整性校验不是秘密认证，授权仍来自显式启用、身份、操作归属和受管队列。

1. CLI 只在读到本次唤醒的新 ready 后发送正文，不能靠发送按键成功推断窗口已打开。
2. 插件严格校验完整一帧。多字、少字、替换、乱序、额外粘贴、非法编码或容量溢出都拒绝；不从脏文本中猜测、提取或修补命令。
3. 完整 LDB1 帧进入 staged 后冻结；CLI 比较操作身份、长度与摘要，再发送专用物理提交键。插件仅发布新的 `receiver_commit_ready` challenge；CLI 的 LDC1 必须与该 nonce、attempt、challenge 和正文摘要精确匹配，插件才 accepted 并 dispatch。后续乱敲不能改变冻结内容；旧尝试迟到的物理键不能执行新 stage。生产离线回归与真机验收分别记录。
4. 明确 rejected 且 accepted=false 的输入污染，才允许原 operation、原业务内容换新 nonce/attempt 整帧重传。默认追加最多两次，总共三次。
5. 单次接收 20 秒，整个重试流程最多 60 秒；0.5 秒、1 秒有界退避，预算到期不再重开。当前 LDB1 编码上限 180 字节，超限明确拒绝；这取代初稿约 256 字节的估计。
6. accepted 回执丢失时先查询原操作；已接受、运行或有报告则继续取原结果。证据不完整或重载后执行效果未知，保留 unresolved，不新建操作绕过去执行。

去重依据为 operation ID 加稳定业务摘要，不使用每次都会变化的接收 nonce。accepted 必须先记录再分发；同一操作不同内容拒绝。跨崩溃不能仅凭内存去重声称 exactly-once。

## 5. 报告、期限与恢复同步修复

| 缺口 | 修改目标 |
|---|---|
| 15 秒观察及外层 2 分钟总期限截断合法执行 | Agent 声明执行预算；CLI 分配加载、接收、执行、持久化、清理预算，总期限覆盖各阶段，不能被隐藏的固定期限截短 |
| 普通输入框焦点造成等待悬空 | 新接收器显式握手；人工工作台焦点路径也补齐，不只监听聊天事件 |
| 编码失败只剩聊天报错和超时 | 独立最小失败编码路径，返回固定错误码和安全的字段路径；失败回执不得再次编码原坏对象 |
| 结果被隐藏后无法取回 | 按精确 operation 查询并重显已有结果；只读恢复不重新执行业务 |
| 超时被写成取消 | 分开表达 deadline、人工取消、未决、执行失败及业务断言失败，按现有退出码合同明确映射 |
| 报告成功等同业务成功 | 分别展示 transport/report、业务断言、cleanup/display 状态 |
| 普通业务恢复依赖手工按 Esc | CLI 使用协议查询、恢复和清理；不触碰聊天草稿或其他输入框。安装/失联的固定重载例外见下节 |

保留现有语义：`live run` 只执行已加载操作；ACK 只确认精确操作，不能隐式重载；finish 同时要求显示已清理；abandon 不代表 ACK、卸载或游戏效果撤销。自动恢复不能突破未决操作的所有权和明确决定要求。

### Agent 决定实验预算，CLI 落实期限

Agent 在准备探针时根据等待事件、采样次数和业务场景声明执行预算，预算随不可变请求保存并送到插件。CLI 在任何执行输入之前校验插件能力上限；超限明确拒绝并给出支持范围，不静默截短。当前异步能力为 1..120 秒，本轮不能仅放宽 CLI 等待就假称插件支持更长任务；扩展范围需同步协议与执行器。

插件报告实际接受的执行预算。CLI 的执行等待覆盖该预算和传输余量，再单独预算加载、SV 持久化与收尾，总期限不能仍固定为 2 分钟。恢复读取原操作的预算、执行进度和截止记录，不重新获得完整执行时长，不重复运行；读取已完成报告和必要清理可使用新的有界恢复尝试。

接收窗口的 20 秒及重试总计 60 秒是独立输入保护期限，不由长探针预算放大。超时分别表示接收失败、探针期限到达或宿主尚未观察到结果；用户取消另行记录。同步 Lua 仍须自身有界，宿主等待期限不能抢占卡死的同步代码。

### 独立的兜底重载

用户明确指定固定原生输入序列：`Esc → Esc → Esc → Enter → /reload → Enter`。这是安装/升级后激活插件、桥无法唤醒或无法连接时的基础能力；不要求旧插件、接收器、session、二维码或桥 readiness 先正常。工作区命令为 `live reload fallback --installation <client> --pid <pid> --request <key> [--session <prior-session>]`；session 关联的 `live reload` 仍保留。兜底重载以 `OP-...` 记录尝试，`live status`/`live resume` 恢复同一尝试，未知输入不重发。完整真机验收仍待记录。

- CLI 明确选定目标窗口及进程身份，持有该窗口输入锁；安装流程沿用选定安装与对应窗口，不向全部客户端广播。首次输入前持久记录 reload attempt、用途、目标安装版本和输入进度；即使没有 session/operation，也能查询这次尝试。
- 只开放这个固定序列，不扩展为任意聊天文本发送器。用户已明确授权这里使用三次 Esc；它是普通路径“不发 Esc、不经聊天兜底”的限定例外。发送由 CLI 的原生输入模块完成，不依赖 Computer Use；前后台投递能力由测试插件和脚本先验证。
- 正常业务使用专用接收器，正常可关联重载保留原机制。安装激活或确认桥不可用时才选兜底；不能用它绕过其他操作所有者、丢弃未决工作、假称 ACK 或撤销游戏效果。
- 每条输入前重核目标身份；中途失败即停止。发送状态与重载验证分开记录。一次尝试后先观察并重新握手；结果未知时保留 pending，不盲目重复 Esc 和 reload。
- 接收器残留模态会吞掉普通 Esc/Enter，原型必须覆盖这一场景。兜底发送前先让自有接收事务释放（可用已验证的紧急解锁或等待不可续期的硬截止），不能把固定序列发进仍在接收协议的 EditBox；此释放不要求桥恢复连接或先读到正常回执。
- 重载后核验目标 runtime、版本、角色及新鲜身份；有原 epoch 时确认变化，旧 session/readiness 失效后重新连接。首次安装无旧 epoch 时，记录新的 runtime 可用和版本匹配证据，不伪造前后关联。无法取得证据时只报告已尝试，不能以按键投递成功、文件时间变化或短暂黑屏宣称安装已激活。

新通道覆盖 identify/connect/reset、状态查询、执行、ACK 和清理。当前 design.md 已有 identify/connect/reset 三种聊天 bootstrap，AGENTS.md 仍只列两种；实施时一并同步为基础接收入口及上述固定重载例外。普通 `/dev` 保留人工工作台入口。

## 6. 整体界面重构

视觉规范统一见根目录 [Design.md](../../Design.md)。参考 Lychee 的设计语义：近黑统一底、暖白文字、少量荔枝红、无装饰横线、无顶部高光、通过留白和字号区分层级。

- 工作台保留宽布局与八个功能页，统一主题、标题、导航、字段和状态控件；不把开发工具压成小搜索面板。
- 二级页面替换正文，返回保留来源状态；齿轮、返回、关闭的大小和 hover 一致。
- Agent 接收框为紧凑的独立窗口：logo、开发连接标题、接收/校验/重试状态、剩余时间与紧急解锁提示，不展示大段协议文本，不弹多余 tooltip。
- 切页、进出和 logo 使用可中断动效；减少动态效果时直接落终态。接收就绪与释放模态不等待动画。
- 中英文成对维护，版本来自安装元数据，不引入本机角色、路径、个人方案或测试信息。

**二维码不改位置：** 始终锚定 `UIParent.TOPLEFT (16, -16)`，保留黑白、四模块静区、现有尺寸规则。不染品牌色、不加圆角、不缩进输入框、不参加动画、不被模态背景覆盖或变暗。二维码布局与新协议内容分别验收。

## 7. 资源和性能约束

基础唤醒注册与调查功能分别计量。未连接时保留最小唤醒入口；调查功能未启用不创建其帧、事件或 hook。接收器、页面和控件按需创建，有界复用；关闭接收器后释放焦点、临时绑定、事件和计时器，保留可复用的有限隐藏控件，不声称已创建 Frame 被销毁。列表使用分页或可见行复用，不无限积累历史、回执和文本。动画只在活动时更新，结束立即清理；没有空闲轮询、永久 OnUpdate 抢焦点或全局键盘钩子。

分别记录冷启动、工作台打开/关闭、一次接收、错误重试和长时间空闲的内存、帧时间及活动资源。强制 GC 只能辅助诊断可回收性，不能代表自然常驻表现。性能优化不能删除证据、缩短合法执行等待或降低输入校验。

后续真机验收须另行在允许游戏操作时进行：Retail 120100、Classic 50504、Titan 38002；不同焦点、输入法、键盘布局、后台窗口、战斗、重载、首次安装/升级、中英文与 UI 缩放。Forever 不纳入已验证矩阵。当前“不在游戏复现”的限制继续有效，本轮不运行这些步骤。
