## 2. 重构范围与业务等价

| 部分 | 目标实现 |
| --- | --- |
| CLI、项目与目标选择、source/LuaLS、data/CASC/DB2/SQL/Hotfix、资产、证据、安装与更新 | 全部由 Rust 实现 |
| Live 连接、执行、恢复、槽位分配、Mailbox 读取、运行时指令/RIP 根定位、Windows 定向输入 | 全部由 Rust 实现；色块、光学心跳与 WGC 按修订要求取消 |
| 游戏内 addon | 保留 Lua，重写必要协议与执行器；游戏内功能继续在 Lua 中运行 |
| npm | 保留包名、命令入口和分发方式；JavaScript 只承担启动及必要的 npm 进程衔接 |
| Go | 迁移期作为冻结的对照实现；最终产品不携带、不调用 Go 后端 |

业务等价覆盖：

- 命令、参数、退出码、JSON/JSONL、分页、错误与覆盖不足的表达。
- 查询结果、导出内容、证据来源和完整性。
- 项目固定引用、缓存隔离、受管安装、更新与中断恢复。
- Live 成功、业务失败、结果未知、清理未完成等不同事实。
- addon 禁用成本、输入释放、战斗限制、secret 值和客户端兼容行为。

以 [command_contract.go](../../internal/command/command_contract.go) 为业务清单，建立“旧行为—新实现—回归用例”逐项映射。parser、help、describe 和 Skill 命令索引继续派生自单一合同，不维护相互独立的命令定义。

保留 `lycheedev.result.v1`、退出码及合法 JSONL `end` 等公开合同；确需改变的公开行为单独列入兼容性决策。协议内部往返和 wire 可以升级，但不能把内部简化当作业务删减的依据。

## 3. Rust crates、模块与依赖方向

采用一个 Cargo workspace，建议从 **7 个产品 crates** 开始。按业务职责和实际依赖划分，不机械复制 Go 包结构和旧状态机。测试工具不计入产品 crates，只有确需独立构建时再决定其组织方式。

| Crate | 职责 |
| --- | --- |
| `lycheedev-cli` | 参数、帮助、describe、输出、错误映射及业务入口组装；生成 `lycheedev.exe` |
| `lycheedev-core` | 共享身份、项目引用、工作空间、存储、缓存、证据、预算及跨进程协调机制 |
| `lycheedev-source` | 源码固定版本、搜索、符号关系、LuaLS |
| `lycheedev-data` | CASC、DB2、SQL、Hotfix、资源读取与导出 |
| `lycheedev-live` | 生命周期、EXECUTE/SETTLE、恢复、槽位预约与发布、Mailbox、运行时指令/RIP 根定位和 Lua 路径验证 |
| `lycheedev-delivery` | 受管 addon/skill 安装、升级、卸载、发行物校验及中断恢复 |
| `lycheedev-windows` | 进程、只读内存、定向输入及系统资源的底层封装；候选产品不含 WGC 通道 |

Source、Data 的业务与回归体系独立，分别建立 crate。安装更新有自己的完整性检查、事务和恢复逻辑，归入 Delivery，不放入 CLI。Core 只承载共享机制和类型，不收纳具体业务以规避依赖问题。

### 3.1 依赖规则

- CLI 组装业务入口与具体适配器，不实现槽位协议、数据查询或安装恢复状态机。
- Source、Data、Live、Delivery 可以依赖 Core；Source、Data、Live 之间不直接形成业务依赖，组合调用在入口完成。
- Core 及需要原生能力的业务 crate 可依赖 Windows。Windows 不反向依赖 Core 或业务 crates，其接口不携带 Live、安装或查询状态。
- Live 通过自己需要的小接口使用受管安装能力，由入口注入 Delivery 的适配器，避免 `live ↔ delivery` 相互依赖。会话激活与恢复仍由 Live 的同一生命周期推进，不能把它们搬到 CLI 再建状态机。
- 具体业务的持久化格式及状态解释由业务 crate 所有；Core 提供原子读写、引用保护、协调与版本检查等机制。

允许的主要依赖方向如下，接口适配不要求业务 crates 互相导入：

```text
cli → source / data / live / delivery / core / windows
source / data / live / delivery → core
core 及需要原生能力的业务 crate → windows
windows → 系统与底层依赖
```

### 3.2 现有交叉依赖的调整

当前 Go 代码中，Live 使用 Delivery 的槽位能力，Delivery 的安装更新又读取 `live/journal`。这些位于不同 Go 子包，不是现有 Go 包的编译循环，但不能按顶层目录原样搬成 Rust crates。

重构时明确调整：

1. 槽位预约、发布、消费与退役归入 Live；Delivery 管理槽位模块的安装文件、版本和受管完整性。
2. 安装占用的共享协调机制归入 Core，Live 与 Delivery 使用同一守卫。Delivery 不解析完整 Live 状态机；检查占用到实际替换期间保持必要的排他保护，不能仅依赖过时的预检结果。
3. 通用证据存储、完整性与引用保护归入 Core，Live 报告解码及业务含义归入 Live，避免通用证据层依赖 Live 协议或桌面能力。
4. 跨业务共用的客户端身份与选择基础类型归入 Core；CASC/DB2 解析仍归 Data，避免 Live 为识别客户端而依赖整个数据业务。

这些调整以实际调用关系和回归用例为依据，不为消除编译依赖而把业务类型无条件上移到 Core。

### 3.3 暂不单拆的模块与验证门槛

Assets 暂留 Data 内部；Mailbox、Protocol、Locator 暂留 Live 内部；LuaLS 暂留 Source 内部。Lua addon 和 npm 启动器保持各自目录，不属于 Rust crates。只有出现明确的独立复用、构建隔离或接口需求时，才重新评估拆分。

7 个 crates 是当前证据支持的推荐起点，不宣称绝对最优。阶段②核验接口和依赖图，阶段③至⑤在真实实现中验证：

- 依赖保持单向，没有通过回调或共享类型隐藏业务循环。
- 各业务可以通过公开接口独立测试，不要求启动整个 CLI 或游戏。
- 接口不大量泄漏内部状态、存储布局或协议阶段。
- CLI 保持入口职责，Core 不演变成具体业务集合。

未满足这些条件时，先调整职责和接口；确有必要才改变 crate 数量，并同步记录依据。

### 3.4 Live 与平台实现约束

Live 对调用方暴露连接、执行、查看、关闭等业务操作。收妥、续办、槽位预约和容量管理隐藏在内部。现有公开命令按兼容清单映射到这些操作，不因此擅自删除命令。

从首次激活开始保留同一份持久生命周期记录。每次调用读取记录，结合当前事实推进；恢复入口复用同一套推进逻辑，不建立第二套恢复状态机。连接、任务和资源清理可作为记录中的不同状态维度，避免一个状态枚举混淆全部事实。

业务逻辑通过明确接口使用文件、输入、时钟和内存读取能力。Windows 句柄、COM/WinRT、原始内存读取及必要的 `unsafe` 集中封装；业务模块不直接操作裸指针与窗口句柄。测试适配器在相同接口注入故障。

进程定向输入、线程与系统资源生命周期需要原生实现。Mailbox 承担全部状态和结果读取，取消 WGC、色块及光学心跳，也不以屏幕截图作回退。保留 opt-in、事件驱动、有界资源、禁用态成本、战斗及 secret 保护要求；新协议须逐项证明其实现。

## 4. 普通任务协议：EXECUTE + SETTLE

正常流程：

```text
持久保存不可变请求
  → 原子发布 EXECUTE
  → 物理输入触发 LoD 加载
  → 游戏私有状态验证并登记接受
  → 执行业务并保留结果
  → CLI 读取、校验、可靠保存完整结果与日志引用
  → 发布 SETTLE
  → 游戏保存收妥记录、释放结果正文
  → CLI 核验确认并记录完成
```

普通任务通常消耗两个槽，Mailbox 状态与结果读取不耗槽。连接、取消、关闭、异常补送仍可能消耗额外容量，不能把“两槽”作为所有路径的固定上界。

### 4.1 发布与授权

发布即授予该不可变请求的执行许可，不代表已经送达或执行。取消逐任务 prepare/commit 往返，仍保留：

- 先持久化意图，再原子发布；发布状态不明时从同一记录恢复。
- 物理输入和受信 LoD 加载入口。
- 完整封套校验，以及此前建立的私有会话、runtime、owner/fence 和 challenge/capability 绑定。
- 输入前的当前进程、窗口、角色、发布字节和新鲜度检查。
- 私有 Receive 先登记接受，再调用业务代码。

Mailbox 仅镜像状态和结果，公开表修改不能授权执行、取消或释放正文。请求摘要覆盖规范化请求、代码和所有影响执行的字段；摘要可检测内容变化，不能单独证明授权来源。

当前代码中的私有状态保证见 [Mailbox 协议](live-mailbox-protocol-2026-10-01.md) 和 [SlotProtocol.lua](../../addon/Bridge/SlotProtocol.lua)。新协议需要重新证明这些保证，不要求保留旧四阶段往返。

### 4.2 结果保存与收妥

SETTLE 包含精确任务身份、结果长度和摘要。发送前必须完成正文持久化、校验及日志引用提交；临时文件或进程缓存不构成可靠保存。

游戏核对自己的私有结果，先保存可重复查询的收妥记录，再释放正文。确认丢失时只查询或重试同一 SETTLE。磁盘满、正文校验失败或日志提交失败时不得 SETTLE。

业务结束即清理执行器登记的监听、计时器和输入占用，不等待 SETTLE。结果核验、业务成败、执行资源清理及正文释放分别报告。资源清理失败不能被收妥成功掩盖。

### 4.3 Mailbox 读取一致性

采用不可变协议记录、精确身份、长度和摘要校验。验证运行时 anchor/根绑定与 Lua 布局，从当前 state/globals/命名 Mailbox 路径读取固定头和完整记录，复核头/尾及认证；前后回读根槽/对象路径，核验进程、映射和 generation。路径、anchor、身份或记录变化时丢弃读取，在原预算内有限重试；不转堆扫描。

撕裂检测、摘要和映射守卫分别证明本次读取的一致性条件，不能独自证明记录新鲜度或来源授权。新鲜度、runtime、目标和私有协议事实需要各自验证。同一 Lua 环境中任意恶意 addon 不因公开镜像与私有表分离就获得完整沙箱隔离。

## 5. 去重、取消、关闭与恢复

任务身份至少包括：

```text
进程实例 + runtime + sessionEpoch + ownerFence + taskSequence + requestDigest
```

主机核验 PID、创建时间、可执行文件及窗口归属；游戏核验自己能独立确认的 runtime、角色、build、会话及私有绑定。不假设 Lua 可以读取 Windows 进程创建时间。

### 5.1 去重与记录保留

- 同一有效 runtime/session 中，同一任务最多进入一次业务执行。
- 同编号、同内容返回已有状态；同编号、不同内容拒绝。
- 高水位阻止历史重放，但不能证明历史任务成功、取消或收妥。
- 当前任务及尚未可靠确认的终态记录不得淘汰。记录有界，保留与淘汰必须有明确确认条件。
- 旧记录不足时返回无法确定的历史状态，不从高水位推断成功。
- 关闭后重开使用新的 sessionEpoch；旧请求、取消和 SETTLE 不得进入新会话。

### 5.2 恢复与 owner

CLI 退出不结束游戏会话。恢复者取得系统锁后读取原生命周期记录，继续同一请求。逻辑 owner 与临时 CLI 进程身份分开，不能仅因 CLI 退出就释放未决任务的逻辑占用。

同一 runtime/session 且去重状态有效时，只有具备相应送达与状态证据，才可在原有效期和有限补送预算内继续同一请求。已接受或执行中等待原任务；已完成重新取结果；已收妥读取小型确认记录。

换 owner 必须经过明确的私有状态与 fence 转换。不能因锁文件年龄、租期或本工作空间查不到日志而抢占。旧输入、旧结果和旧 SETTLE 不能影响新 owner。

运行时因 reload、退出或换角色变化时拒绝旧请求。证据不足保留执行结果不确定；不自动跨 runtime 重跑有副作用的任务。

### 5.3 取消、时间和不可中断 Lua

- 发布前允许本地取消。
- 发布后必须取得游戏取消确认；只停止 CLI 等待不构成取消成功。
- 取消与执行竞争时，以私有状态先接受的动作决定结果；取消登记先于 EXECUTE 时拒绝迟到执行。
- 已开始只能协作停止后续工作，不承诺回滚已有副作用。
- 请求有效期、执行预算和 CLI 等待时间分别定义。时钟来源与重启恢复规则必须明确，重试不重置预算。
- 不可强行中断的 Lua，不能因主机超时而声称已停止。

游戏已产生副作用、尚未记录结果时崩溃，是不能消除的不确定窗口。本方案保证同一有效运行时内最多执行一次，并恢复可证明的状态；不承诺任意外部副作用的全局 exactly-once。

## 6. 500 个 LoD 槽与共享安装

当前 [SlotRuntime.lua](../../addon/Bridge/SlotRuntime.lua) 会向前加载空槽和其他 runtime 的槽；这些加载也消耗本实例的 LoD。因此只把 200 改成 500，再预留两个物理槽，不能证明任务一定有容量收尾。

推荐设计：

1. 每个安装目录生成 500 个 LoD 模块。
2. 安装级账本统一管理磁盘槽位预约，各 runtime 独立记录已加载集合。
3. 连接时授予实例明确的槽位路线和配额，并保存到游戏私有会话状态；绑定后只沿自己的路线推进。
4. 首次绑定使用独立、有界的引导容量，不侵占执行中任务的收尾容量。
5. 接受 EXECUTE 前同时保证执行、SETTLE、有限重试和必要关闭容量。
6. 已加载 LoD 在该 runtime 内绝不复用。磁盘文件释放与游戏槽位可复用分开处理。
7. 正常容量换代只在没有未决任务的空闲点发生，只 reload 目标实例。
8. 容量不足时有界排队或返回明确背压，不覆盖其他实例的预约，不按 TTL 丢弃未知任务。

**待原型定稿项：**槽位路线表示、引导区大小、配额分配与回收、路线换代、最大并发实例数，以及迟到输入对容量的影响。

原型必须证明：其他实例的推进、迟到唤醒、退出和恢复不会耗尽已接受任务的收尾容量。引导耗尽不能使已有业务失去结果；实例配额回收必须基于准确消费或 runtime 退役证据。窗口未响应时不能依靠无限重试维持容量承诺。

原型阶段通过离线模型、真实 Lua 5.1 和故障注入验证，不提前安排人工游戏验收。涉及真实客户端加载、输入和目录缓存行为的证明保留到最后的统一人工验收。

500 是每安装目录的槽数，不等于 500 个任务或无限并发实例。对外支持的实例上限和资源上限在原型验证后写入 capability，并按该上限进行压力验收。

200→500 升级需要版本化安装账本、中断恢复和全部文件校验。每个在线 PID 分别激活并证明真实 inventory；磁盘更新不等于运行时或客户端目录缓存已经更新。

## 7. Mailbox 运行时指令定位与 Lua 路径读取

### 7.0 参考实现与职责

2026-10-12 用户最新要求停止私有堆扫描，参考版本由最初提及的 `2.5.1` 更正为 Go `v3.1.0`（Git 提交 `9edc06b4591264eaac68e34575bc02f750ffe758`）。已核该版本的 [lua_mailbox_recipe.go](../../internal/live/memory/lua_mailbox_recipe.go)、[lua_mailbox.go](../../internal/live/memory/lua_mailbox.go) 及 `internal/live/channel/native_windows.go`；相关文件与当前 Go 相同。这里的 `3.1.0` 是定位实现参考版本，不是本次产品版本变更。

定位为 `OpenNative → OpenLuaMailbox → ResolveLuaMailboxRoot`，读取为 `module base + Lua root RVA → Lua state → globals → LycheeDevInternal → Mailbox`。指令匹配读取实际映射的运行时代码，根 RVA 由当前有符号 RIP 位移算出；不扫描磁盘指令，不调用 wowdump，不沿用固定数值 RVA。

Go 仍用锁定磁盘 EXE 的 hash/PE 元数据签发布局；按用户“不考虑 exe”的要求，这部分不进入新定位入口。Rust 新入口由 OS 固定进程/模块范围并核验运行时定位字段，不读取或哈希磁盘 EXE，也不以磁盘布局、EXE hash 白名单或静态方法定稿作为准入条件。Lua 布局适配、当前路径和协议验证仍是必需项。

| 层 | 职责 |
| --- | --- |
| Windows RuntimeModule | 从持有的进程句柄和 OS 模块库存固定 base/size/架构/映射，只授权选定模块内的有界只读访问 |
| RuntimeRootRecipe | 匹配指令模板、解析 RIP、验证全部操作数/唯一性/稳定性，签发不可伪造的根绑定 |
| Lua Mailbox reader | 从根重新解析当前 state/globals/命名表/字段，验证类型、secret、身份及完整记录 |
| 统一协议推进器 | 独立核验认证、exact command identity、本次观察、有效期和持久化事实；定位成功不授予输入权限 |

### 7.1 运行时匹配与 RIP 解析

1. 固定指定 PID/创建时间、只读句柄和窗口归属，读取 OS 主模块库存。模块 base/size/架构与当前映射由 OS 能力提供，调用方传入 RVA 不能获得读取权限。
2. 有界解码实际用于定位的运行时 header/section 字段，限定当前可读、可执行代码区。运行时 VirtualAddress 不能当磁盘 raw offset；不得机械复用通用磁盘 PE parser。受保护的 Machine/SizeOfImage 等非定位字段不能通过修补、归一化或猜测获得信任。
3. 仅在选定模块运行时 `.text` 分块匹配已审查模板，位移使用通配符，跨块保留模板尾部。所有模板的原始命中先参加唯一性判断；零/多命中明确 unavailable，不能先丢弃无效 RIP 候选再声称唯一。
4. 按固定指令边界计算 `targetRVA = anchorRVA + instructionOffset + instructionLength + sign_extend(disp32)`。核验溢出、模块范围、每个操作数 1/4/8 字节宽度和目标段权限；根槽须 8 字节对齐，位于可读/可写/非执行数据段，call 目标须在合格代码段。Forever 重复 getter call 的目标必须相同。
5. 签发前重读完整 anchor、根槽、定位元数据并核验进程/模块映射。已知 anchor 可优先验证，但只有已建立本进程当前代码区唯一性证明时才可作快路；首次定位仍完成有界匹配，不能以磁盘 hash 代替运行时代码唯一性。每次从当前指令重新解算，旧 RVA 不能跳过验证。失效仅在原总预算及固定次数内重新匹配，没有私有堆扫描回退。

### 7.2 沿 Lua 路径读取

从当前根槽读取 Lua state → globals → `LycheeDevInternal.Mailbox`，按命名 hash/table lookup 读取精确字段/键。state、TValue、table/node/string 布局来自已验证的 client/build/recipe/layout profile；不按标准 Lua 记忆猜偏移，不默认不同 build 或 Asia/CN Beta 共用布局。

每次重新遍历路径，检查指针范围、当前合格映射、类型/tag、secret/restricted key/value、节点数、collision chain、字符串长度、schema/release/runtime，前后回读 anchor、根槽及完整对象路径。GC、reload 或路径变化时丢弃该次读取并有界重试。只点读当前路径指向的私有对象，不扫描堆、不缓存 heap 地址作为事实。

不可变记录先固定头、再完整读回核验头/尾、长度、摘要及协议认证；BODY 只有在已验证当前终态绑定 exact task/长度/摘要后准入。路径稳定、根绑定、layout 和 checksum 都不独自证明新鲜度或授权；nonce/完整 command digest、私有签名、总有效期和实例身份继续按最终协议核验。

### 7.3 资源、隔离与验收

Go `v3.1.0` 的参考上限为 header 1 MiB、代码区 128 MiB、每块 1 MiB、最多 2,048 次模块读；单次 Lua lookup 最多 512 次读/1 MiB。不是 Rust 已通过的统一预算。Rust 须计入全部 OS 查询、模块/私有点读、候选、分配、anchor/path 复核、重试和重定位，共享请求总截止及取消；同步系统调用没有硬抢占承诺。定位覆盖、路径一致性、认证与业务完成分别报告。

同 build 多实例可共用不可变 recipe/layout 描述；module base、动态根绑定、state/对象指针、runtime、publication baseline 和窗口按 PID/创建身份独立核验。reload、退出、PID 重用、模块重映射或身份变化不继承旧根或授权。

验收覆盖 ASLR、跨块指令、正/负 RIP 位移、零/多命中、无效操作数、重复 call 不一致、受保护 header、不可读/重映射、anchor/root/path 改变、GC/reload、secret/tag、撕裂/长度/摘要、取消/截止及释放。Retail、Classic、Titan、Forever Asia Beta、Forever CN Beta 的 recipe/layout 和同 build 多实例分别由同一最终 Rust 候选证明。

此前 `Find/Lookup/Scan/FindNearby` 私有堆原型及其测试保留历史范围，停止作为产品路线、回退或验收门槛。现有 Rust 磁盘 locator/exact-hash layout 门须改为 RuntimeModule/RootBinding 及统一预算接线；不能直接声称实现了本节。设计修订不表示 Live 可用、协议审计或实机验收通过。


## 8. 多 build 与同 build 多实例

| 层级 | 身份与隔离范围 |
| --- | --- |
| 客户端与数据 | product、地区、build、locale、固定数据引用；数据内容身份与 Mailbox 定位分别验证 |
| 共享安装 | 规范安装路径、实际文件身份、协议版本、槽池世代 |
| 进程实例 | 只读进程句柄、PID＋创建时间、OS 映像路径、当前窗口归属 |
| 游戏会话 | runtime、角色、sessionEpoch、ownerFence、任务序号 |

不能以目录名、build 字符串、PID 或角色名单独标识一个运行实例。解析路径别名，确保指向同一实际安装的访问共用协调资源。

同一进程即使来自不同项目、不同 `--home`，也只能有一个活动推进者。系统锁释放不代表未决任务消失；其他工作空间不能因本地没有历史就绕过恢复。

共享安装只短暂串行化文件发布和账本修改。等待游戏或执行业务时不持有安装级写锁。固定锁顺序，避免窗口锁、安装锁和存储事务互相等待。

不同实例可同时执行业务；单实例内部保持单任务。一个实例 reload、退出、卡住或换角色时，其结果和预约按自身证据恢复，其他实例身份、正文、输入和 owner 不受影响。

同一实际安装只能有一致的受管协议与槽池版本。升级需协调该安装的全部在线实例，不能让不同版本向同一物理槽写入不兼容内容。

现有 [implementation-status.md](implementation-status.md) 已记录指定正式服版本同安装双实例验收及首次失败后的恢复。历史记录用作场景来源，新协议与 Rust 实现必须重新验证。当前最终范围为 Retail、Classic、Titan、Forever Asia Beta（`wow_classic_beta`）、Forever CN Beta（`wow_cn_beta`）；覆盖单实例、同 build 同安装至少双实例、至少两个 build 同时在线，以及不同 build 各自多实例混合。实例上限须明确并按上限压力验收，缺少客户端或证据时保留未验收。

复用现有 Lua、协议样本、固定探针、Node/npm 测试及 [baseline](../../tests/baseline/README.md)。Go 单测按行为迁移，旧行为用例与新协议替代用例建立映射；不能以删除旧测试消除失败。真实 LuaLS、必需 Lua 5.1 和版本/Skill 门禁继续保留。

差分只规范化明确非业务字段，例如临时路径、运行时间和随机 ID；保留身份引用关系、摘要、覆盖和错误差异。遇到旧实现已确认的缺陷，单独建立修复用例与兼容性记录，不把旧缺陷强制当作正确结果。

### 9.1 必需故障矩阵

- 在请求落盘、临时文件写入、原子发布、输入、游戏接受、执行结束、正文保存、SETTLE 和确认各边界强制终止 CLI。
- 输入已入队但回执丢失、业务有副作用但结果未形成、收妥完成但确认丢失。
- 重复、乱序、迟到、同编号异内容、取消竞争、关闭重开、owner/fence 切换。
- Mailbox 撕裂、陈旧记录、公开表篡改、GC/布局变化、摘要和长度错误。
- 磁盘满、文件被占用、发布中断、安装迁移中断、PID/窗口复用。
- 500 槽边界、引导耗尽、路线换代、收尾预留、迟到按键、同安装竞争。
- 最大接纳实例数同时运行，并故意让一个实例不唤醒、卡住或退出，验证背压、公平性和收尾容量。

### 9.2 必需真机矩阵

- 支持矩阵中各 build 的单实例正常、异常、异步、大结果和恢复。
- 同 build、同安装至少双实例；压力覆盖最终声明的最大实例数。
- 多 build 同时在线，以及不同 build 各自多实例的混合场景。
- 单个实例 reload、退出、换角色、卡住，其他实例继续执行且身份和结果正确。
- 禁用/启用、首次安装、200→500 升级、relogin、战斗、输入法及快捷键冲突。
- 连续运行跨越容量换代，最终结果归档正确，预约、owner 和执行资源按预期清理。

有副作用的真机任务不能为差分盲目重复执行，使用可控探针和独立运行记录。保存首次失败、原任务恢复、截图与日志，不把重试后的通过改写为首次全绿。

性能基线包括运行时指令定位冷启动/锚点复核/失效重新匹配/无缓存、Lua 路径及 Mailbox 读取、任务往返、500 槽加载、内存和系统资源释放。按修订目标，固定主要业务冷/热、典型/大负载矩阵，各场景 Go/Rust 交替各至少 20 个样本，Rust 中位耗时不超过 Go 的 50%，并分别报告 p95、CPU、峰值内存、读写量和资源释放。取消的光学/WGC 能力作为兼容差异列明，不用删掉仍保留的业务换取性能通过。未执行项保留 `not_run`，离线 fixture 不替代真实客户端证据。

阶段②优先通过静态材料、离线原型和自动测试解决技术不确定性。不要先完整翻译旧 Live 状态机，再开始简化。运行时指令/RIP/根绑定及 Lua 路径验证、500 槽多实例容量及新协议恢复的设计和离线验证未闭环时，不进入全面 Live 替换；真实环境适用性统一由最后的人工验收确认。

阶段①至⑥完成后应交付同一份可运行候选、自动测试结果和人工验收步骤，再进入阶段⑦。人工验收发现问题时回到对应实现修复，补跑受影响的自动检查并重新形成候选，再复验受影响的人工场景。不得因人工验收后置而提前声明实机通过。

最终人工验收通过后，才具备发行切换条件；正式发布仍按后续授权和发布门禁执行。候选包组装与隔离验证不等于发布。

迁移期间 Go 基线保持可执行，按变更范围执行原有检查；新增 Rust 构建、静态检查和测试逐步纳入同一基线入口。最终移除 Go 构建门禁前，必须完成用例映射与替代门禁，不能留下验证空档。

实施继续使用本工作树，不因阶段变化额外创建工作树、分支或 PR。提交、推送、发布按后续任务授权执行。

最终完成要求同时满足：

1. 公开业务有对应回归，并对所有兼容性差异作出明确处理。
2. 产品不依赖 Go 后端或 wowdump。
3. 500 槽的引导、执行、收妥、恢复、关闭和容量换代闭环成立。
4. 对外声明支持的多 build/多实例矩阵有真实客户端证据。
5. 未决任务、未知结果与资源清理能够准确报告和恢复。
6. Rust 发行物满足现有完整性、源码重建、隔离安装与发布契约。

## 13. 实施期间新增的明确要求

2026-10-08 用户追加以下目标，纳入同一重构任务，不授权提前发布或提前进行人工游戏验收：

1. 参考固定的暴雪源码，在业务等价、禁用成本、战斗与 secret 保护不变的前提下，优化 addon CPU 与内存。自动 fixture 和最终真实客户端 CPU/内存证据分别记录。
2. Source 引入 tree-sitter-lua 与真实 LuaLS；语义与关系查询效果须优于旧解析路径。原始源码读取仍可用于必要调查，不将一次 grep 失效推广为禁止读取源码的通用规则。
3. CLI 默认返回小而有意义的结果，保留准确 pin/path/lines、why-match、范围、覆盖不足与截断事实，以及可执行的下一步/游标。新增投影不能静默删除公开 coverage 或证据；模板/AST 关系不伪称 LuaLS 语义结果。
4. 使用 `$skill-creator` 更新版本化 Skill，按能力渐进披露。命令只引用实际可用合同；最终新上下文独立 forward-test 从真实请求和原始材料执行，不提供作者答案。
5. `source validate` 加入固定 Lua 5.1.5 `luac -p`。现有 `lycheedev` npm 包携带 Windows amd64 的原生 `luac.exe`、身份/哈希清单、许可与对应源码，不依赖系统 PATH 或外部运行时 DLL，不额外创建独立 npm 包。精确官方来源 SHA-256 为 `2640fc56a795f29d28ef15e13c34a47e223960b0240e8cb0a82d9b0738695333`。
