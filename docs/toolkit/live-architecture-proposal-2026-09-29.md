# Live 架构收敛方案：每实例统一推进，明确共享资源保证

状态：主机部分已实施于工作区，共享槽位协议仍为原型；不是发布或实机能力承诺。2026-09-29。
当前落地范围与缺口见[实施记录](live-channel-implementation-2026-09-29.md)。
基于当前 worktree、三项离线复现、原 Retail 会话恢复证据，以及 skill-creator 原则。
本文不变更现行命令合同；所有新增字段和接口均为拟议设计。
二次审计已修正范围；理由、代码证据与方案比较见
[架构复审](live-architecture-review-2026-09-29.md)。主机职责方案可采用；共享槽位协议待原型准入。

先读这六条即可理解实施范围：

1. 保留目前验证过的内存通道、证据、安装和资源互斥；共享槽位布局允许必要的局部演进。
2. 各入口先看游戏现在是什么状态，再推进原请求；旧业务阶段不能禁止观察和恢复。
3. 业务发键、reload、关闭各查各自必要条件，恢复不依赖业务成功。
4. 安装、进程实例和 runtime 分开管理；短锁保护磁盘事务，实例配额保护接纳后的可用容量。
5. CLI 决定怎么恢复，Skill 决定查什么及如何解释；原请求续跑不重置总预算。
6. 主机整改与协议原型分别验收；固定按键和 64 槽优先复用，原型通过前不承诺共享槽位故障隔离。

正文 1–10 定义职责与合同；14–17 给出最小改动、执行顺序和验收。

## 1. 决策

采用小型单体：每实例一个执行负责人，依据持久目标和事实推进；底层只执行确定动作。
保留 Go CLI、只读内存、Lua 执行器、项目证据库与受管安装机制。64 个 LoD 和固定
Ctrl+Alt+F12 是协议原型优先复用的基础；单文件单预约已经证实存在恢复闭环，不能
继续作为所有目标都必须保留的约束。主机整改本身可独立交付，但不等于槽位隔离完成。
Agent 保留实验设计权，确定性的通道编排由 CLI 承担。

健壮的含义是：在声明的故障范围内不重复未知副作用、不串实例、有界退出、保留准确证据，
并在条件满足时可继续；不承诺任意第三方吞键或进程崩溃后仍能自动完成。
简洁的含义是减少独立决策者与状态组合；高效的含义是复用现有快路径，避免额外扫描、
安装大锁和无进展的恢复循环。三者都由后面的验收门槛约束。

目标是三个可检验的性质：任何阶段均可观察现实；关闭/恢复不依赖业务成功；
重试资格由精确证据和请求身份决定。状态记录仍然必要，但不再让多个可变阶段共同决定
是否允许观察、恢复和判断完成。

现有设计文档已提出唯一协调器，实际仍由 Bound、Operation.Stage、Transaction.Phase、
Reload.Phase、Recovery.Phase、Closing 的组合控制入口。仅把这些分支移到一个大函数
不构成架构改进。新方案必须删除旧决策路径，并以跨阶段不变量验收。

## 2. 当前证据

| 事实 | 架构含义 |
| --- | --- |
| Continue 仅在 Bound 且 reload 已结束时发现替代 runtime | 观察能力错误地依赖旧推进状态；首次绑定与 reload 前变化均可能卡住 |
| reload 与 invoke 共享包含 nextSlot 的输入校验 | 非槽位控制继承业务投递前置条件，丢回执会连恢复入口一起堵住 |
| Wake 加载 engine.NextSlot() | 键本身不指向请求；重复/延迟键可能消费后续负载 |
| Skill 要解释 stage/waiting 并决定 resume | Agent 仍是第二个恢复决策者；异常处理分散于代码和自然语言 |
| 每次命令重建 WithTimeout | 单次等待有界不等于整项任务有界；连续 resume 可不断获得新等待时间 |
| ProbeExecution 只执行登记的 cleanup 回调 | resourcesReleased=true 不是第三方 UI/任意副作用已恢复的证明 |
| runtime-investigations.md 仍要求 ACK/receipt cleanup | 命令存在性检查不能识别跨传输语义串用 |

前三项缺口的复现见 live-channel-robustness-audit-2026-09-29.md。
UI 吞键和历史 CLI 并发的具体因果仍未证实，不以推测作为设计事实。

## 3. 模块职责与依赖

```text
用户意图
  ↓
Skill：选目标 / 设计实验 / 判断可重复性 / 解释证据
  ↓ 目标、不可变请求、预算、已授权的恢复范围
CLI 应用入口：校验请求，转换为持久目标
  ↓
协调模块：读取证据 → 获取观测 → 决定一个动作
  ├─ 证据存储：目标、请求、动作意图/结果、报告、历史
  ├─ 观测模块：固定进程、候选 runtime、owner、回执、输入状态
  ├─ 控制模块：准确绑定、运行时恢复、释放连接
  └─ 投递模块：受管发布、精确请求投递、接收端去重
            ↓
Lua 协议模块 → ProbeExecution 资源作用域 → 业务探针
```

这是职责划分，不要求建立四个公共框架或四套调度器。协调模块只有一个动作选择器。
现有 Windows adapter 与离线故障 adapter 穿过相同接口，真实变化处才设 seam。
Source/Data/Assets 不依赖 Live 状态：沿现有 pinned references、索引和资产链工作。
安装模块继续负责磁盘完整性，安装成功与游戏激活成功保持分离。

### 必须保留的已有成果

| 已有设计 | 本轮处理 | 证据/保护要求 |
| --- | --- | --- |
| 原生只读内存、精确记录校验、缓存可丢弃 | 复用，不另造 reader | 缓存开关、失效缓存的正确性相同；保留 coverage/truncation |
| 64 槽位、prepare/commit、准确 nonce 回执 | 优先复用握手与按键；集合格式需版本化验证 | 未知输入不重发，结果确认后再释放 |
| 安装短发布锁＋持久槽位预约 | 保留防覆盖原则；集合原型调整预约粒度 | 已有正常双实例通过不代表未知预约下无阻塞 |
| 精确进程生命周期、同实例排他与输入临近复核 | 复用 | 不按窗口标题、角色名或 build 合并实例 |
| 先日志意图、后输入事实、内容摘要与日志轮转 | 保留存储实现 | 不用另一份数据库/状态文件成为并行权威 |
| ProbeExecution 的有界异步、Callback、OnCleanup、短输入保护 | 保留并澄清清理范围 | 不让普通探针持有输入保护，不新增 idle hook/timer |
| CLI 命令表、生成引用、受管安装与发布链 | 保留 | 不发布未实现命令，不复制源文件覆盖受管安装 |
| source/data/asset 固定引用与独立证据链 | 不改 | 通道改造不能让离线查询依赖游戏连接 |

先前实测是这些设计值得保留的依据，不自动计入本轮新代码验收。
特别是 2026-09-28 同目录双进程：短锁争用恢复、各 13 次查询、单边 reload、
最终 pending=0/claim=0 已有证据，见 live-input-shared-installation-2026-09-28.md。

### 多 build、多实例是核心资源模型

| 资源 | 主身份 | 共享范围 |
| --- | --- | --- |
| 安装 | 规范化目录/文件系统身份＋受管安装记录 | 物理槽位、安装维护、磁盘 release |
| 实例 | PID＋进程创建时间，窗口身份附加校验 | driver/连接 owner、输入目标 |
| runtime | 实例身份＋准确验证的 runtime token | consumed slots、报告、去重、角色绑定 |
| 发布 | 安装＋物理槽位＋负载代际/摘要＋准确 consumer | 从发布到消费/退役证据明确前不可覆盖 |

build、product、release、协议能力用于验证兼容性，不用作实例键。
同 build 不同安装资源独立；同安装多进程共享文件、不共享 consumed 集合；
跨 build 独立安装可同时工作，客户端差异集中在 Compat/catalog 与能力适配。
同目录磁盘升级而旧实例仍运行时，磁盘 build/release 与每个实例加载版本分别记录。

锁职责固定为：每实例一个 driver；安装发布只保护短文件事务与投递核验；桌面共享
输入资源只在发键短区间串行化。内存扫描、Lua 执行和结果等待不占安装/桌面输入锁。
保留现有已验证的锁顺序；维护先阻止新接纳，再在不持发布锁时核验全部受影响实例，
不能为了升级 A 而忽略正在运行的 B。新进程加入和清单不完整时重新核验或明确阻塞。

共享安装示例：A 对槽位 4 的消费未知时，B 不得覆盖它；A 的旧回执晚到，
只能收尾 A 的准确预约，不能清掉 B 后来合法发布的另一代负载。
A reload 不换掉 B 的 runtime；A 进程退出只能退役 A 的 consumer。
系统输入的共享性不等于所有实例共用一个业务队列。
配额归固定实例生命周期，不能通过换 CON/runtime 刷新；共享磁盘损坏或桌面输入故障
仍会影响多实例。当前 fence 恒为 1，不代表已有可接管租约；保留不抢占活跃 OS driver
的规则，不为套用模式新增接管。若未来允许接管，另行设计递增代际及接收端拒绝旧请求。

## 4. 用目标和证据替代相互覆盖的阶段

持久化的权威信息：

- 固定目标：安装、PID/创建时间、窗口绑定、角色约束。runtime 是会变化的代际，不是目标本身。
- 用户目标：保持可用、完成准确请求、关闭连接；显式 reload 是受范围约束的控制请求。
- 不可变业务请求：request ID、目标、代码摘要、执行预算、重放声明。
- 动作证据：计划、发送前意图、已知零发送/已提交/未知、准确回执。
- 结果证据：原始报告、确认关联、持久化与资源收尾事实。
- 持久总预算和允许的恢复动作。

请求去重范围明确为 `(项目, CON, request key)`，同 key 的代码/预算/策略必须一致。
恢复沿原 CON/操作；新 runtime 是新尝试，新 CON 则是新连接，不能凭同 key 重跑原
unknown 操作。暂不新增项目级请求服务；跨 CON 接管不属于当前保证。

connecting/running/closing 等只作为派生显示，不再各自成为驱动真相。
证据记录单调增加；更换 runtime 追加新代际，不改写旧请求为“没执行”。
继续使用现有日志、快照与内容引用及其恢复契约；不额外引入完整事件溯源框架。
快照不能形成另一份独立状态权威，也不要求绕过现有轮转对全部历史反复回放。

协调接口在概念上是：

```text
Decide(goal, durableFacts, observation) -> oneAction | completion | blocker
```

它不执行 IO，不持锁等待。执行器先保存动作意图，再调用 adapter，最后保存事实。
重启后对同一动作收敛；跨多个命令的请求身份从日志恢复，不依赖 Agent 记忆。

## 5. 观察先于业务推进，但候选身份不构成授权

所有入口都可以发现目标进程和候选 runtime，包括首次 bind、reload intent、等待回执和 closing。
有效缓存只影响扫描顺序。不要为每个 reducer 步骤做全内存扫描：复用同轮有效观测，
未知/失效时做有界重读或发现；发键前仍作必要的临近复核。

候选身份、输入就绪、准确绑定分开：发现新 descriptor 不允许发业务；
使用新挑战验证 runtime、owner、目标，再退役旧资源。无命中/扫描缺口不是进程退出证据。
窗口丢失不等于 PID 生命周期结束。秘密值、权限不足、战斗和用户持键仍保留 unknown/blocker。

## 6. 控制与投递使用不同前置条件

| 动作 | 必须验证 | 不应错误继承 |
| --- | --- | --- |
| 只读发现 | 固定进程身份、读取权限、候选格式/覆盖 | Bound、业务阶段、nextSlot 一致 |
| 槽位投递 | 新鲜绑定、目标、owner/fence、精确负载/槽位/代际、输入资格 | 其他请求完成 |
| reload | 固定目标、归属、运行时/安装资格、输入资格、恢复范围 | 主机旧业务 nextSlot 等于游戏当前值 |
| 正常关闭 | 所属资源与准确 unbind 证据 | 业务报告一定成功 |
| 进程退出退役 | OS 证明原进程生命周期结束、准确资源归属 | 活着的 Lua 回执 |

控制动作依然遵守原子发布及跨进程互斥。共享安装里，未知消费的物理文件不能被另一
实例覆盖；“控制独立”不代表跳过共享预约、原 owner 或保护边界。
关闭不能等同于取消已发生的业务副作用。若必须销毁 runtime，保留未知结果和恢复证据。
没有获得 reload 权限、正在战斗或输入不可用时，应明确阻塞，不暗中升级为重启客户端。

## 7. 协议决策：v1 修复与集合原型分别验收

现有 next-slot 快捷键使安全重试受限。本轮继续禁止未知输入重发：优先取得原回执；
无法取得时，在既有授权、目标/归属和新鲜输入资格满足后使用一次已记账的 reload，
经新 runtime 准确绑定完成旧资源退役。reload 本身结果未知时也不重发。
条件仍不满足，返回可解释、可恢复的阻塞，不用反复 resume 伪装进展。

v1 的主机整改不能解决 slot 1 未知预约闭环。同安装多实例继续作为产品要求时，
优先原型验证有界集合、每实例份额及恢复预留；原型通过之前不正式迁移协议。
集合必须验证路由身份歧义、加载无匹配后的耗槽行为、原子合并和容量上限，详见 §18。

精确寻址保留为备选研究，不擅改现行固定按键合同。可研究的方向是：输入激活指向一个准确物理槽位，
槽位封套再绑定 runtime、请求 ID、摘要、owner/fence；重复激活已加载槽位只查询/返回
该次投递状态，不推进下一槽。不要简单重发现有 Wake。

可行性实验需验证有限绑定/硬件事件能否在各 pinned 客户端可靠寻址，以及已加载 LoD
如何安全返回原回执；不在本文凭记忆认定 WoW API 支持。验证还必须包括迟到键跨 reload、
跨物理文件代际复用、共享安装两进程，以及用户现有绑定冲突。

寻址只解决 next-slot 误消费，不能单独解决迟到输入或 exactly-once：

- prepare 仅装入待核验数据，不执行；commit 仍绑定准确 challenge 和代码摘要。
- 控制与业务按准确 exchange/request 去重；保留已释放请求的有界 tombstone。
- 回执必须可按原 exchange 查询；内存扫描旧字符串不可冒充当前 fresh confirmation。
- runtime 换代后未知 opaque 副作用仍未知；允许重复的 observation 也受明确策略和总预算约束。
- 保留结果/去重表/控制容量在接纳前预留；满时背压，不删除未确认结果。

主机整改保持未知输入不重发和显式 runtime 恢复限制，不把它描述为端到端恰好一次。
不要为消灭 pending 而退回任意重发，也不引入另一套隐蔽传输。
不建议改用内存写入/注入、常驻后台进程或轮询游戏文件来解决本问题。

## 8. 并发、预算和完成语义

一个固定游戏实例只有一个执行 driver；同请求重复调用可以读进度，不能另起 writer。
busy 返回持锁调用的可诊断身份和同一请求引用；不得以超时或关窗为理由强抢活跃 OS 锁。
若没有经过验证的跨进程取消通道，就不承诺立即打断另一调用；单次调用本身必须有界。

三类预算明确区分：Lua 执行预算、单次 CLI 等待时间、持久恢复总预算。
resume 不刷新后者；可靠的进展增加 progressVersion，不自动赠送预算。
系统时钟回退/机器重启不能悄悄扩充预算，存储截止时间和已消费额度，异常保守停止自动动作。
关闭/退出退役保留独立而有界的收尾预算，任务预算耗尽不能禁止必要的资源回收。
业务请求、显式 reload、首次 close 各有准确目标及一次初始化的额度；重复 close、
resume 和 CLI 重启共用原目标预算。预算限制自动推进，读取既有证据不受影响；
延长额度必须是明确且留痕的决定，不能靠改 request key 续同一个关闭目标。

调用取消/超时仅停止本次等待，不表示探针停止或清理完成。持久停止目标必须在新业务
动作选择前生效；已经发布的 commit 仍可能被迟到键执行，不把停止接纳说成撤销副作用。

建议结果增加以下结构化信息（拟议字段，不是现有命令合同）：

```json
{
  "request": {"id": "...", "status": "blocked"},
  "connection": {"status": "closing"},
  "operation": {"outcome": "unknown", "report": "candidate"},
  "cleanup": {"runtime": "pending", "probeResources": "unknown"},
  "continuation": {
    "kind": "wait_active_driver",
    "requestId": "...",
    "progressVersion": 17,
    "remainingBudgetMs": 12000
  }
}
```

可区分 completed、continue、wait_active_driver、wait_external、needs_decision、
budget_exhausted、failed；这些是调用结果分类，不新增七个持久协议状态机。
等待结果必须附具体 blocker：资源引用（实例/安装/slot/预约/活跃调用）、解除条件、
原请求是否可继续、进展版本。OS 短锁忙、未知预约、输入阻挡不得压成一个普通 pending。
只有具体条件变化或已有调用完成才继续；没有观察机制时有界退出，不让 Skill 忙等。
退出码保持既有 0/2..8 合同并明确映射。业务失败但报告取回成功不得误报传输失败。

## 9. 探针资源与清理

沿 ProbeExecution 建立显式资源作用域，提供有界的 timer/event/frame 清理辅助接口，
回调统一经过 Callback；业务 success/error/执行预算到期沿同一清理路径。
只有执行端确实收到并支持的取消才能触发取消清理，CLI context 取消不具备这个含义。
已有第三方 UI 的打开、选择和恢复由探针声明并在变更前登记清理；不得推断任意 Lua 的副作用。

将“登记资源已释放”和“外部状态已恢复”分别报告。没有登记外部资源时不能默认为外部
清理成功。注册与静态 lint 只能发现部分问题，不能证明 UI 所有权或恢复正确。
临时打开原本关闭的窗口可登记关闭；用户原本已开的窗口不能被通用 cleanup 擅自关闭。
异步回调失效与同步 Lua 无法被宿主强制抢占的限制继续保留。
清理回调失败必须保留具体义务，不能盲目重跑可能有副作用的 callback；必要时使用
已授权的换代收尾或返回 blocker。runtime 销毁不证明第三方业务状态恢复。

## 10. Skill 编排：一个薄入口，按任务加载参考

按 skill-creator 的“只保留改变决策的信息”和渐进披露原则，保留一个 lycheedev skill。
Source/Data/Assets/Validation/Live/Installation 的路由已有实际用途，无需拆成多个相互
转交的技能，也不修改系统 skill-creator 本身。

Skill 负责：用户目标和授权范围、固定目标/版本、选择证据、编写小而有界的实验、
判断完整实验是否可重复、解释报告及未验证项。
Skill 不负责：阶段图、槽位算术、重发资格、nonce、退役次序、锁修复、reload 后重绑定。

入口只保留路由、稳定项目/请求身份、风险范围与返回值解释。Live 参考只保留实验设计、
资源清理、continuation 类别及证据解释；原生协议阶段说明移到维护者文档。
安装失败、旧 QR 历史和性能调查等条件知识按需加载。将性能参考的旧 ACK 描述改为
当前传输的统一收尾，旧历史明确隔离。安装到用户目录的技能只能由同一 release 管理，
repo skill 是唯一编辑源，不能并行维护两个修订版本。

目标编排规则（待 CLI 能力落实后才写进正式 Skill）：

1. 在既有授权内解析固定目标；仅身份歧义或真实范围缺口需要用户选择。
2. 使用不可变请求和预算执行；报表生成/查询不应为形式完整而连游戏。
3. CLI 自行完成预算内恢复。单次工具等待返回时，Agent 只按类型化 continuation
   继续原请求，不解释内部 stage，不重建 request key。
4. continue：同一请求串行续跑；wait_active_driver：观察既有调用，不并发轰炸。
   wait_external：等条件变化；needs_decision：只问真正缺少的决定。
   budget_exhausted：报告阻塞，不能用反复 resume 变相续期。
5. 已验证失败报告照常收尾并解释业务失败；未知结果不重跑 opaque 工作。
6. 任务需要结束时请求 close，由 CLI 完成清理或返回准确义务，不把 pending 标成 done。

恢复范围来自用户原授权，可在请求内固化；声明 observation 不是自动获得改 UI、
安装、reload 或修改业务数据的权限。也不为已授权的常规恢复反复索要许可。
probe_settings 点击了开关，其整个实验并不因目的叫“观察”就天然可重复。

不新增 PowerShell/JS 重试脚本：脚本会产生第三套恢复逻辑。薄 launcher 继续只找 CLI。
也不把“每次先全量研究全部 API”写成普遍强制流程；复用已经固定且适用的证据。

## 11. 验证策略

协调模块测试使用真实决策/日志与故障 adapter，在每个持久化、输入、回执与结果边界
注入中断；采用表驱动或模型序列测试覆盖所有目标与观察类别组合，不只给每个 stage
补一个 happy path。核心不变量：

- 任意业务阶段均可观察 runtime 变化，但未经准确绑定不执行业务。
- 无 known-not-sent 或协议证明，不重发未知副作用。
- close 不启动新业务；结果 unknown 不妨碍有证据的资源退役。
- 无重复 writer、无跨实例抢占、无未知物理槽位覆盖。
- deadline/resume/崩溃不刷新总预算；缓存开关不改变正确性。
- 只对已验证并持久化的报告宣称 verified；所有 truncation/coverage gap 可见。

协议改造有独立跨语言测试及真实客户端门槛。Retail/Classic/Titan 分别记录；
Forever 仍为实验档。离线通过不替代硬件键、combat、reload、relogin 和共享安装实测。

Skill 验证除 quick_validate 和 skill-contract 外，应增加独立场景评估：
active driver、重复 request、验证成功但 cleanup pending、opaque unknown、无进展 pending、
输入阻挡、不同角色候选、UI 清理遗漏、source-only 请求、旧传输参考干扰。
评估 observable 行为：是否串行、沿原 ID、预算是否保留、是否越权、是否误报成功。
不按段落/关键词匹配判断编排正确，不向评估者透露预期结论。
本轮只设计评估，未运行独立 agent 或新增 Skill 的行为验收。

## 12. 迁移顺序与删除清单

1. 固定外部结果和 continuation 合同、观察/授权/预算不变量；把三项复现纳入验收。
2. 实现独立观察、停止优先与按动作校验，替换旧 Continue/next 的阶段门控，修复 v1 已知主机缺口。
   新协调器接管后删除旧路径；上一轮 reconcilePending 止血分支不作为永久平行入口。
3. 统一 connect/execute/resume/reload/disconnect/activation 的目标接纳和结果投影。
   CLI 吸收预算与串行编排，Skill 同 release 更新；新增能力未落地前不改文档去假装可用。
4. 澄清现有 ProbeExecution 的资源作用域与清理证据语义；只有实际重复代码需要时
   才增加资源辅助接口，不建立通用 UI 自动回滚框架。
5. 完成有界集合的隔离原型准入；通过后才迁移 Go/Lua 协议、安装与日志版本。
   原型未通过时不得把主机完成写成共享槽位隔离已完成。
6. 完成故障矩阵、Skill 场景评估及各客户端/多实例实测；精确寻址保留为备选。

未来若实施 v2，必须显式协商 capability/日志 schema。本轮若演进日志也需显式版本检查。
旧未知事务由对应版本继续恢复或凭进程
结束证据退役；不把 input_attempted 改写成 unsent，不在原 live 安装上混用新旧协议。
离线迁移先在日志副本回放；读兼容与写升级须明确，新 schema 不能让旧 CLI 静默误解。

应删除：命令层独立完成判断、Skill stage 分支、反复 resume 的隐式总预算、
重复恢复脚本和与原生通道冲突的 ACK 指引。
继续复用：内存扫描器、桌面精确窗口输入、发布预约、证据摘要、清理回调执行器和
固定来源数据链。实际接口可能演进，不以“全部复用”限制必要修正。

## 13. 取舍

补三个 if 成本最低，但保留组合复杂度；直接重写全部工具链风险高，且对 source/data 无收益。
仅重写 Skill 无法修复代码门控，常驻 daemon 也不能消除未知输入与跨 runtime 证据丢失。
推荐“复用传输基础与存储 + 每实例统一推进 + 控制条件解耦 + 共享容量隔离 + Skill 瘦身”。
主机收敛可消除错误门控；共享槽位闭环需要协议原型通过后才能承诺解决。
同安装集合是当前部署要求下的候选；若需要物理文件故障隔离，独立安装更直接，但不
擅自改变用户部署方式。外部输入的未知结果和有限容量仍是明确能力边界。

## 14. 从前两轮承诺到本轮改动

| 既有承诺/已验证事实 | 当前差距 | 本轮最小整改与删除项 |
| --- | --- | --- |
| 单一 Continue 推进 | 观察受 Bound/reload 阶段门控；状态变化发现不完整 | 把观察和身份收敛放在公共前序；删除阶段阻止发现的条件 |
| 输入按事实判断 | reload 误用槽位编号一致性 | 按动作划分校验；保留 invoke 的精确槽位校验 |
| 所有入口统一恢复 | bootstrap、reload、runtime recovery 各有局部推进 | 共用目标接纳与代际收敛；物理激活方式作为 adapter 能力差异 |
| unknown 不重放 | Agent 仍解释阶段与重复续跑 | CLI 提供 continuation、进展证据和持久预算；删 Skill 内部阶段决策 |
| 干净收尾 | 第三方资源未登记也可能 resourcesReleased=true | 明确清理范围；不把未登记当成已验证恢复 |
| 安装发布不锁住其他实例 | 已有专项实测支撑 | 不重写这部分，以原基准保护它 |

重构允许保留必要的事务内部阶段；禁止把“状态派生”解释为重写全部日志格式、
每步全量回放或把所有状态变成一个巨大的 reducer。公共动作选择只有一处，
发布、验证与资源释放仍由现有专职代码完成。旧函数只有在调用方迁移且测试覆盖后删除。

## 15. 公共推进顺序与停止条件

每次推进按下列职责顺序工作；这是命令期间的有界调度，不新增后台进程或游戏轮询门禁：

1. 在实例 driver 下读取并验证原请求、预算与动作证据；重复调用不能成为第二个 writer。
2. 获取所需观测：进程生命周期、runtime 候选、归属。可复用仍有效的准确观测；
   不能因旧业务阶段拒绝发现新 runtime。
3. 优先处理已接纳的 close/停止目标：不再产生新 prepare/commit；按下表安排观察和收尾。
   进程退出有 OS 证明时直接精确退役。活进程的关闭只获取所需证据；不能无条件先重连
   再决定是否关闭。现行销毁证明仍需 fresh bind 而被阻塞时，明确说明未完成。
4. 按当前目标收敛代际变化：继续业务须准确新绑定；旧事务留存后退役，业务结果按原
   证据分类。用户自行 reload 达到换代目标时记录“观察到换代”，不谎称 CLI 发送成功。
5. 没有关闭目标时推进准确业务请求；按当前事实选择一个动作，执行前持久意图，
   发键前临近核验，之后持久事实。回执缺失不是零发送。
6. 达成目标即返回；等待调用/外部条件、达到预算或需要决定时返回具体原因。

初次绑定尚未知角色身份时，仅执行最小身份/绑定流程，不从不完整观测推断用户选择。
身份确实改变时停止原目标的输入，不能把“允许恢复”理解为跟随另一角色或新 PID。
当所有候选都只有历史内存证据时返回 unknown，不能因样本最多、地址最新或 token 最大就授权。

关闭行为表（按已发布副作用判断，不只看主机阶段名称）：

| 已知事实 | 关闭动作 |
| --- | --- |
| prepare 尚未发布 | 本地停止请求，收尾已有连接；不再发 prepare |
| prepare 已发布/接受、commit 未发布 | 不发送 commit 换取退出；v1 无 abort，取回准确状态后用已授权 reload 或返回阻塞 |
| commit 已发布且是否执行未知 | 保留 unknown；不重发、不承诺取消，尝试原回执及有界收尾 |
| 已运行/报告可取 | 取回报告并正常 release；停止接纳与业务结束分别报告 |
| 原 PID 生命周期已结束 | 只退役该实例确切资源；已验证报告保留，未知执行不改写 |

已经发布的 commit 即使本次已知零发键，也可能被先前迟到键消费。

## 16. 简洁与性能的实现门槛

- 不新增 daemon、消息总线、第二套持久任务库、重试脚本或第二种内存扫描器。
- 一次新观测只驱动有限的本地步骤；新鲜采样序号增加不等于任务有实质进展。
- 缓存命中不能无条件触发全内存发现；绑定/确认所需准确验证继续保留。
- 原 pending 轮询不得每次开启重复完整扫描；同轮可批量读取兼容的记录，
  缺失/失效后在剩余预算内恢复发现，缓存 miss 本身不允许无限重置工作量。
- 快照用于避免反复解析全部历史；继续沿用有界轮转与内容寻址，避免每次 Esc 复制代码/报告。
- 有效动作和证据关联必须先正确，再做性能优化；不能靠放宽 freshness 或跳过校验达标。

实施前冻结旧版本的冷/热/禁用缓存、正常查询、失联恢复、同目录双实例基准。
比较端到端耗时、扫描次数/字节、锁持有时间、CPU/内存峰值、日志增长和业务执行次数。
正常快路径不增加协议往返；不可避免的额外验证必须说明原因。性能是否回退用相同
机器/输入/多次采样评估；在取得基线前不编造毫秒或百分比指标。等待游戏/用户的时间单列。

## 17. 本轮验收矩阵与交付边界

| 场景组 | 必须满足的结果 |
| --- | --- |
| 三项已复现缺口 | 各自永久回归转绿；同一公开入口可继续或返回真实 blocker，无死等旧 runtime |
| 每个副作用的崩溃边界 | 意图前/后、发送后、回执后、结果落盘后中断都不重复未知业务 |
| 已消费但回执丢失、未消费且键被吞 | 能区分证据范围，均不盲发；控制恢复不继承旧槽位一致性 |
| 重复 resume、并发 execute/disconnect | 一个 writer；原请求/nonce 不换；close 不启动新业务 |
| 单实例 reload/relogin/进程退出/PID 复用 | 不串目标；仅准确退出证明允许无游戏输入退役 |
| Retail/Classic/Titan 多 build | 各自能力和 fresh timebase 验证；一个通过不外推其他；Forever 独立记录 |
| 同 build 不同安装、多 build 独立安装 | 业务可并行；输入短区间正确仲裁；无跨安装预约 |
| 同安装双实例 | 争同槽、不同槽等待、迟到回执、单边 reload/退出、同时容量换代、升级竞态 |

| 资源清理与禁用状态 | success/error/timeout/late callback 覆盖；不增加未授权 idle 成本；清理范围诚实 |

每项分别记录 offline 与 live。任何必需项 not_run 就不能宣布本轮整体完成。
设计稿通过自检不等于实现健壮；全量 Go/Lua 绿也不能代替多实例硬件输入验收。
发布仍服从现有版本、CI、受管安装和不可变包合同，本方案不授权发布。

交付时必须附：保留模块清单、删除旧路径清单、逐项回归结果、同条件性能对比、
原日志兼容/恢复办法与未解决限制。不能只交一张新架构图或几个新抽象名称。

## 18. 共享槽位并发：安全与可推进性分别验收

补充决策：同 build 多实例是否争槽，取决于是否共享安装目录。不同安装不共享物理文件；
现行 v1 下，同安装 A/B 都需要 slot 4 时，只能先后发布两个负载。这里的串行是物理传输约束，
不是把两个实例的整个业务执行串行化。

当前实现已做到：PublishSlot 拒绝覆盖未知消费的预约，Native.Publish 释放短发布锁后
返回 shared_publication；发键前再次核验原负载；ConfirmSlotConsumed 只处理准确 nonce。
这解决覆盖/误消费风险，不自动证明公平、无饥饿或一个故障实例永不阻塞另一实例。

v1 主机整改必须分别处理四种情况；这张表不描述候选集合的能力：

| 情况 | 应有行为 |
| --- | --- |
| A/B 同时需要同一物理槽 | 有界争用，胜者完成发布/消费后释放预约；败者保留原请求，不能另起请求抢占 |
| A 的槽已消费，业务仍异步执行 | 不等业务结束，准确消费回执持久化后允许 B 复用文件；A 的已加载 Lua 不依赖后续磁盘字节 |
| A 等战斗/焦点或 CLI 退出，消费未知 | 释放 OS 短锁但保留预约；B 若需要同槽会受阻，若需要其他可用槽应能推进 |
| A reload，B 的未知预约挡住 A 新 bind 所需槽 | 必须呈现准确依赖，不能无期限假装一般 publication 等待，也不能删除 B 的预约 |

现行协议只调用 nextSlot，不能因 slot 4 忙就让同实例跳用 slot 5。把槽位按 PID 分区、
增加锁、增加槽位数量，都不能单独解决这个约束。维持 v1 时目标只能是安全、有界且
可诊断的背压，不承诺故障实例之间完全互不影响。

改进限定在有证据的地方：发布前做一次输入资格预检查以减少明显不可投递时抢占槽位，
发键前仍必须复核；一旦有可能被迟到键消费，不能凭“本次零发送”撤销负载。
争用结果包含 installation/slot、预约 consumer/runtime/request 引用、已知进展和阻塞原因；
不泄露无关探针内容，不替其他 owner 发键。公平性通过并发压力测试度量，当前 OS 锁
不能被描述为 FIFO；若出现实质饥饿，再论证有界仲裁机制，不预先添加持久队列。

特别风险：当前 RuntimeRecovery 先新 bind 再退役旧预约，而新 runtime 从 slot 1 开始。
若 slot 1 被本实例旧未知 bind 或另一实例未知负载占用，存在恢复依赖闭环的代码路径风险。
本组合现已由真实发布/预约/日志路径离线复现，见
[槽位并发前置验证](slot-concurrency-feasibility-2026-09-29.md)；游戏观测与输入为测试 adapter，
不冒充完整实机复现。已有正常双实例通过不能排除这个闭环。
新 descriptor 不能代替 fresh bind 证明旧 runtime 消失，TTL 也不能授权覆盖。

要满足共享安装中已接纳实例的有限故障隔离，必须改变单文件单未知预约语义，
或实证另一条控制/寻址路径。前置实验已确认主机收敛不足，§7 不再承诺协议不变。
集合原型通过前，产品只能声明 v1 的安全背压，不能声称已独立恢复。

新增准入用例：同槽争用、消费后业务长跑、发键前/后 CLI 崩溃、旧回执晚到、slot 1
预约下单边及双边 reload、新实例加入、三实例长期竞争。断言分别覆盖无覆盖、无重放、
准确 blocker、其他可用槽进展、预算有界和每个实例的等待时间，不只统计最终成功率。

前置验证后的范围修订：仅主机收敛不能兑现共享槽位的故障隔离。优先验证有界多封套
文件，保留固定按键和 64 LoD；它是局部协议候选，不是本轮已实现能力。具体不变量、
LoD 一次性限制、容量和升级门槛见上述验证记录。现有 Skill 已包含固定目标等基本规则，
后续应补 CLI 的准确阻塞信息与预算，而非重复添加禁止语句。

集合原型额外要求：

- 按固定实例接纳和限额，普通业务不能使用恢复预留；reload/换 CON 不能重置份额。
  冻结最大实例数、每实例业务/恢复成员数、最大字节及最坏故障序列容量推导。
- 冷启动及同 build 路由身份必须无歧义；冲突拒绝，初绑挑战在固定进程核验。
  主机知道 PID 不意味着 Lua 能区分所有实例，不能只凭随机 token 宣称绝对唯一。
- 无匹配/格式拒绝仍可能已经加载 LoD，必须记录耗用和明确推进结果，不等原槽重读。
- 成员不可变摘要与物理集合版本分开；追加、删除、旧回执、崩溃恢复只作用于准确成员。
- 接纳范围内且目标可输入、路由无歧义、存储正常、容量预算未耗尽时，一个未知成员
  不应迫使其他已接纳实例等待该成员结束。超出假设明确背压，不宣称无限故障隔离。
