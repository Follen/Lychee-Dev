一、全量业务覆盖与等价

以冻结的 Go v3.1.2 的 89 条公开命令及参数合同为完整清单，建立“旧行为—Rust 实现—回归用例—验收证据”映射。

覆盖 Source、Data、Assets、Live、项目管理、证据管理、安装、升级、卸载及恢复。

验证正常结果、必要参数组合、退出码、JSON/JSONL、分页、截断、错误、取消、超时和中断恢复。注册命令不等于实现完成，模块测试通过不等于公开命令全部通过。

本次明确取消色块、光学心跳和 WGC 相关能力，须在兼容清单中记录；其余业务保持等价。正确性改进可以保留，但须说明差异及依据，不得借重构删减业务或降低查询质量。

最终产品运行不调用 Go、Python 或 wowdump。Go 仅作为冻结的回归对照，不进入产品运行链路。

二、重新制定 Native Live 协议

围绕实际业务目标重新设计完整、统一、可实现、可验证的协议。

已有协议、代码和 EXECUTE + SETTLE 草案仅作为参考。2026-10-12 用户明确选择四槽 exact COMMIT 文件方案：正常独立任务包含 RUN 与 RECEIVED 两条逻辑命令，每条分别使用 STAGE 和不可变 exact COMMIT 两个 LoD，合计四槽、四次正常触发；Mailbox 读取另按预算计数。具体载体见 [exact COMMIT 方案](rust-native-protocol-exact-commit-2026-10-08.md)。两槽 token 路线保留历史比较证据，不再作为当前实施选择或必须继续比较的门槛。

选定四槽路线不代表完整协议已经定稿或审计通过。主机验证本次认证状态、持久化精确授权后才发布 COMMIT；结果可靠保存后才确认收妥。每安装仍为 500 槽；正常容量换代在无未决任务的安全点自动 reload 目标实例并重新建立连接。执行中、结果未可靠保存或输入不确定时先恢复收尾；引导、重试、取消、关闭及换代的额外槽位成本和多实例隔离仍须实现并验证。

新协议必须满足：

1\. Mailbox 是唯一的状态、输入条件、回执和结果读取通道。取消色块、光学心跳及 WGC，不保留光学回退。
2\. 每个受管安装提供 500 个 LoD 槽，支持多 build、同 build 多实例和共享安装下的实例隔离。
3\. 在业务等价的前提下，减少正常任务往返、重复状态、常驻开销和恢复复杂度。
4\. 没有有效 Mailbox、读取失败、状态过期、加载或 reload 中，不得发送业务按键。首次安装激活单独定义，避免依赖尚未建立的 Mailbox，也不能成为绕过正常校验的通用入口。
5\. Mailbox 表达角色、runtime、输入就绪、战斗、焦点及阻塞原因。输入前核验当前实例和新鲜状态，游戏侧执行入口再次检查条件。
6\. 游戏侧私有状态决定请求是否被接受。修改公开 Mailbox 不能授予执行、取消或释放结果的权限。
7\. 不确定输入不得盲目重放，超时、进程退出或记录丢失不能被解释为业务成功或失败。
8\. 队列、结果、历史记录、内存读取、重试、等待和资源使用均有明确上限。

协议必须明确：

\- 参与者、信任边界及各方能够观察和证明的事实。
\- build、安装、进程、窗口、角色、runtime、会话、owner 和任务的身份与绑定规则。
\- 消息格式、版本、字段含义、状态转换、前置条件和拒绝行为。
\- 首次激活、连接、输入就绪、提交、接受、执行、取结果、收妥、取消和关闭。
\- 结果持久化、执行资源清理、正文释放和历史记录淘汰的顺序。
\- CLI 中断、游戏退出、reload、角色切换、owner 变更及容量换代后的恢复。
\- 多实例槽位分配、共享安装协调、收尾预留、容量耗尽及最大支持实例数。
\- 旧版本升级和未决事务处理，禁止猜测转换或覆盖未决记录。
\- 成功、失败、未知、清理未完成及后续操作的对外表达。

交付协议文档、正常与异常时序、状态转换表、核心不变量和简化依据。

协议审计与自动化原型验证闭环前，不开展大范围替换。允许编写必要原型验证设计，人工游戏验收仍放最后。

三、充分审计协议并验证实现一致性

由未参与相应设计的独立审查者，以新上下文审计协议，主动寻找反例和无法实现的承诺。

审计至少覆盖：

1\. 正确性：接受条件、状态转换、结果保存和释放顺序；明确区分未发送、发送不确定、已接受、执行中、已完成、结果未知和清理未完成。
2\. 恢复：重复、乱序、迟到、同编号不同内容、回执丢失、取消竞争、关闭重开和重试；覆盖关键持久化、发布、输入、接受、结果提交及资源释放边界的中断。
3\. 隔离：PID 重用、窗口变化、角色切换、旧 runtime、旧 owner、旧请求和旧结果；验证多实例及共享安装不串任务、不串结果、不覆盖资源。
4\. 读取与授权：公开 Mailbox 篡改、读取撕裂、布局错误、陈旧状态和客户端暂停不得错误授予输入或执行资格。
5\. 活性与资源：死锁、循环等待、无法收尾的恢复、预算重置、泄漏、500 槽容量边界、换代失败及实例上限。
6\. 简洁性：每种消息、状态、持久记录和后台活动均有必要用途；正常与恢复复用统一推进逻辑，不靠重复机制掩盖问题。

每个审计问题保留反例、处理决定和复核结果。审查不能代替实际验证。

使用 Rust 推进器、真实 Lua 5.1 接收端、状态模型和故障注入验证协议。每条核心不变量和每类关键故障都映射到可执行测试或明确的最终实机验收项。

只有影响正确性、隔离、恢复和有界资源的问题全部解决，正常及关键故障矩阵自动验证通过，才能定稿协议。实机专属假设须单独列出，不提前记为通过。

实现后核对代码、持久化格式和实际行为是否符合最终协议。实质性协议变更须补做相关审计与回归。

四、Mailbox 运行时指令定位与 Lua 路径读取（2026-10-12 最新修订）

参考 Go `v3.1.0`（提交 `9edc06b4591264eaac68e34575bc02f750ffe758`）：在选定进程主模块的运行时代码区有界匹配指令特征，解析有符号 RIP 位移，动态求出 Lua 根 RVA，再沿 Lua state → globals → LycheeDevInternal → Mailbox 读取。停止私有堆暴扫，不保留 Find/Lookup/Scan、hints 或附近搜索作为产品定位/回退。

分别证明：

1\. OS 固定进程/窗口/模块身份、范围与映射；代码区有界匹配、跨块、全部命中唯一性及 RIP 操作数校验；
2\. 动态 root binding、anchor/root/定位元数据稳定性，各 client/build 的已验证 Lua 布局；
3\. 当前 state/globals/命名表/字段路径、类型/secret/长度、完整记录、认证及本次观察；
4\. ASLR、GC、reload、重映射、PID 重用、多 build/同 build 多实例隔离与有界失败。

匹配输入是当前运行时代码；新入口不读取或哈希磁盘 EXE，不使用 EXE hash 白名单、磁盘布局前置门禁或磁盘静态方法定稿。参考 Go 的运行时 recipe/RIP/Lua 路径实现，模块身份与范围改由 Rust RuntimeModule 的 OS 能力固定；不机械复用磁盘 PE parser，不修补或猜测受保护 header，不继承旧数字 RVA。无法验证模板、根或 Lua 布局时明确 unavailable，禁止堆扫描回退或业务输入。

根/路径命中只证明读取条件，不证明当前 runtime、就绪或成功。公开篡改、历史复制、陈旧状态、矛盾记录、路径变化或读失败不能授权输入；BODY 由已验证当前终态绑定 exact task/长度/摘要后准入。全过程共享字节、OS/read 调用、候选、分配、重定位次数和请求总截止；重试不重置预算。

此前堆扫描代码、静态研究及失败保留各自历史范围，不转为新路线通过。详细设计见总方案第 7 节。

五、从第一性原理重新设计 Source

目标是提供准确、可追溯、可复现、资源有界的 WoW 源码研究与插件检查能力。Source 的设计由这些业务目标决定，不以保留 LuaLS、LSP、现有 broker、缓存结构或 Rust 接入层为前提。

允许重构整个 Source 内部实现，保留必要的公开命令及业务合同。已有成果经过核对后复用；不合理的结构可以替换，不因已有投入继续叠加补丁。

1\. 先明确业务合同和分析对象

在固定暴雪源码及客户端环境上，完整支持搜索、定义、引用、调用关系、上下文、flow 和 validate，以及相关同步、索引、差异、会话管理和清理命令。

明确各能力回答的问题、所需输入、结果含义、完整性条件、无法确定时的表达、预算及分页规则。

分析输入必须绑定源码身份、精确内容、客户端 API 环境、配置、分析引擎版本和分析规则版本。分析固定输入，不执行被调查源码或仓库内的可执行配置。

查询结果必须能够追溯到原文件、位置和实际依据。明确区分文本命中、语法事实、语义绑定、推断关系与运行时未知行为。

2\. 优先评估 EmmyLua Analyzer Rust 的直接库集成

以 EmmyLua Analyzer Rust 的解析库和语义分析库作为首选候选，优先评估直接调用 Rust 库，而非仅将 LuaLS 可执行文件替换成另一套 LSP 服务。

实现阶段核对并固定上游版本或 commit、许可证、依赖、工具链及实际可用接口。上游宣传和功能列表不能替代本项目验证。

原型至少验证：

\- Lua 5.1 与 WoW 源码的语法、作用域和语义适配。
\- 定义、跨文件引用、别名、调用关系、类型与诊断能力。
\- 完整 Retail 源码的构建、重复查询、内存占用和资源释放。
\- 客户端 API、插件加载关系及 XML 内联脚本的接入。
\- 取消、超时、分析失败及缓存失效后的行为。
\- Windows amd64 离线发行和对应源码重建的可行性。

通过原型证据决定最终引擎及接入方式。若 EmmyLua 存在必需能力缺口，明确记录缺口、补足成本和替代方案；不得隐藏缺口、降低质量，或未经比较重新回到 LuaLS 接入层持续修补。

tree-sitter-lua 是否保留由独立职责和实测收益决定，不再将同时使用 tree-sitter-lua 与 LuaLS 作为验收前提。避免为同一事实维护多套无法核对的解析或符号系统。

3\. 围绕统一分析事实设计内部结构

将固定输入、Lua 分析、WoW 环境适配、查询结果和执行资源管理的职责明确分开。

搜索、定义、引用、调用关系、上下文、flow 和 validate 应复用可核对的文件、位置、符号和关系事实，避免每个命令自行扫描、猜测绑定或管理分析进程。

明确符号身份在同一快照中的稳定性、跨快照比较规则及失效条件。分页和后续查询必须绑定原分析快照，不能混入新文件或新环境。

WoW 适配须正确处理 TOC/XML 加载关系、共享全局环境、客户端 API 声明、常见 Mixin 用法及动态访问。无法静态确定的关系必须保留不确定性，不能制造确定答案。

固定 Lua 5.1.5 的 luac 继续承担语法兼容检查。luac 随现有 npm 包提供，通过 stdin 检查 Lua 文件及 XML 内联脚本，并映射原文件位置。不依赖系统 PATH、安装时下载或外部运行时 DLL。

“goto label”和“::label::”必须被 Lua 5.1 检查拒绝，合法的 goto 标识符必须接受。

4\. 根据资源和故障要求决定进程与缓存设计

优先验证由一个受控分析进程直接加载 Rust 分析库的方案。需要跨 CLI 复用时，由该进程直接持有分析状态，避免无必要的 broker、worker 和语言服务器多层转发。

最终是否使用独立进程、常驻状态及持久索引，由故障隔离、取消能力、内存和性能证据决定；不得假设 Rust 库天然不会崩溃、内存不足或无法及时取消。

请求预算、分析状态、缓存、进程、句柄及租约必须具有明确所有者和统一生命周期。队列、并发、缓存、消息、结果和等待均有上限。

缓存键必须覆盖实际影响结果的全部输入。缓存复用不能混淆不同源码、客户端、引擎或规则，也不能将未完成结果标记为完整。

取消、超时和分析进程异常退出必须返回可解释的状态。通信中断不得伪装成业务成功，也不得在没有证据时猜测为内存不足或用户取消。

请求结束与错误返回应有明确的收尾规则，避免分析预算耗尽后无法返回错误。必要收尾时间计入既定总预算，不通过额外无界等待掩盖问题。

5\. 用业务正确性验证查询质量

查询质量不得低于旧版，并以明确用例证明新增分析能力有效。

覆盖作用域、遮蔽、跨文件、别名、表成员、常见 Mixin、动态访问、注释与字符串伪引用、Unicode、XML 位置映射、分页、预算和截断。

建立具有明确预期结果的用例，并与冻结 Go 版本进行公开命令对照。Go 结果仅是对照证据；发现旧版错误时，以固定源码事实和可复核用例判断，不复制旧错误。

flow 和调用关系须明确实际支持的推导范围，不能将词法邻接、文本命中或可能调用描述为已证明的控制流或确定调用。

明确区分输入覆盖、分析完成、结果截断和结论不确定。正常支持场景不得靠长期返回 partial 通过验收。

6\. 完整输入、重复使用和故障验证

在完整 Retail 源码输入和既定预算内，通过冷启动、同一会话连续查询、跨 CLI 复用、缓存命中与失效、取消、超时、关闭、重开和 prune。

测试必须同时包含真正执行分析的重复查询及缓存路径，不能让缓存遮住第二次或后续分析失败。

正常支持负载必须完成；资源不足时明确报错并回收进程、句柄和租约。重复运行不得持续累积资源，不得通过缩减源码、减少语义查询、关闭必需能力或提高预算换取通过。

验证故障发生后的下一次正常查询，防止取消、超时或崩溃污染后续状态。

7\. 处理已有失败证据并完成迁移

保留已有 AV、异常 EOF、内存不足及生命周期失败的原始证据，逐项记录已确认事实、未确认原因、涉及路径和新设计中的处理方式。

仍保留的实现路径必须完成必要诊断、修复及回归。被整体移除的旧实现不要求继续修补，但必须说明对应风险如何由新设计处理，并以相同业务输入和相关故障测试验证。

删除旧路径不等于证明旧故障根因，一次成功也不等于稳定性问题解决。未确定的历史原因应如实记录。

先完成设计和最小完整原型验证，再迁移公开命令、缓存、会话管理、打包和 Skill。替换完成后清理不再需要的运行依赖和旧接入逻辑，避免长期维护两套默认分析链路。

交付 Source 设计说明、引擎选型证据、能力与质量矩阵、资源及性能报告、旧问题处理映射和迁移验证记录。

六、性能目标

Live、Source、Data 分别按“同等工作耗时减半”验收：Rust 中位耗时不超过 Go 的 50%。

测试前固定覆盖主要业务的基准矩阵，包含冷启动、热缓存、典型负载和大负载，不能只挑选快路径。

固定同一机器、输入、输出范围、校验强度、缓存状态及可比较的优化构建；Go/Rust 交替运行，每个场景各至少 20 个样本。

每个必需场景独立判断，同时报告 p95、CPU、峰值内存、读写量和资源释放情况，不用整体平均掩盖未达标场景。

参考固定暴雪源码优化 addon CPU 和内存，提供同等业务场景的前后证据；保持禁用态成本、战斗限制、secret 保护及业务效果。

验证幂等、未决事务处理、用户改动保护及中断后继续执行。
