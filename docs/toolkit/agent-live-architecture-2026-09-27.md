# Agent 驱动的 Live 架构方案

状态：r4 架构与验收候选，用户已批准实施，前置实验及接口尚未全部冻结。2026-09-27。审计依据见 [方案审计](agent-live-architecture-audit-2026-09-27.md)，通过/失败规则见 [可靠性验收合同](agent-live-acceptance-2026-09-27.md)，进度见 [实施记录](agent-live-implementation-2026-09-27.md)。未通过的门槛不因开始实施自动关闭。

本文件是拟议的下一版设计，不代表已实现、已安装或已验收。工作区已有探索性改动，尚未形成可交付版本；不得把这些改动当成方案已经确定的依据。没有继续委派子代理。

## 1. 产品目标与范围

Agent 选定客户端，提交一个调查，拿到可验证结果；常规情况下一个执行命令完成加载、必要的 reload、运行、报告读取、ACK、清屏和释放占用。中断后恢复同一个调查，不要求 Agent 理解二维码、按键、队列和内部阶段。

本次重构覆盖 Live、游戏桥、工作台 UI、CLI 契约和 skill 编排。保留 source 的 Git/worktree/LuaLS 能力、data 的 SQL/DB2/hotfix 能力和 assets 导出；它们通过固定引用与 Live 联合使用，不被拖进 Live 状态机。

不承诺任何环境下零故障。必须做到：不误选目标、不把发出输入当成功、不重复执行结果未知的代码、不漏掉收尾义务；不能完成时给出准确结果、当前允许的下一步及其前提。外部条件未变且没有安全进展时明确返回阻塞，不强造一个自动动作。

## 2. 对 Agent 的接口

以下是拟议接口，正式命令目录仍以 describe 输出为准。

```text
lycheedev live instances --passive
lycheedev live connect --installation <path> --pid <pid> --snapshot <pin>
lycheedev live execute --session <session> --file <probe.lua> --request <key> --budget-seconds <n>
lycheedev live status <operation>
lycheedev live resume <operation>
lycheedev live abandon <operation>
```

- `instances --passive`：拟增加的显式被动枚举，只读安装和窗口，不发送唤醒。角色尚未验证时返回未知。现有 `instances` 默认主动识别的含义保留，不静默变更旧调用，不再增加 discover 同义入口。主动识别按已授权的安装/PID范围执行。
- `connect`：只识别所选窗口并建立已验证连接；选项不足且有多个候选时返回候选，不选前台或列表第一项。
- `execute`：接受文件或已有不可变 probe revision（二选一），冻结源代码、预算、目标、数据 pin 和完成要求。默认完成整个调查。
- `status`：只读证据，不唤醒游戏。
- `resume`：继续原任务剩余工作；已经完成时只读返回。不会改目标或重新给业务一次执行机会。
- `abandon`：明确放弃未决任务的收尾，保存证据并释放允许释放的占用；不声称游戏内副作用已撤销。

保留现有 `probe put/load`、`run`、`ack`、`finish` 对既有原子任务的含义。新 skill 的默认路径使用 `execute`，原子入口放到高级说明。完整任务有单一的完成目标 finished，不能通过原子命令降低它；不能满足这一点的原子调用明确拒绝并给出 resume，而不是偷偷运行旧的“ACK后释放”路径。bugs、独立 reload 等保留专用业务类型，共用调查机制，不改写成通用 Lua 包装。

同一 workspace、稳定窗口实例和 request key：输入完全相同则返回/恢复原 operation；代码、预算、角色、build、pin 或完成方式变了则返回冲突。查重必须在 reconnect 或发送任何输入之前完成，并在取得跨工作区准入后重检。不同目标可以使用同名 key，仍对应不同任务。

稳定身份只含规范化安装/产品/build、进程启动身份/HWND/可执行文件和 actor；不把窗口标题、发现来源、观测时间、当前 session record ID 或 epoch 放进不可变请求摘要。按 operation 恢复时读已保存代码、预算和报告位置，不要求原文件仍存在、不跟随可变 probe 名称、不重猜账号目录。只有新提交请求才读取源文件并比对冻结摘要。跨调用选候选需要携带完整实例指纹的候选引用，PID 过滤本身不是历史目标凭据；候选引用仍须重新验证，不能授予输入权限。

预算分四类：宿主单次调用等待、输入接收、协作式探针执行、报告与清理观察。探针预算由 Agent 指定；Async 截止从请求开始执行计算，晚调用 Async 不重新计时。业务预算不包含游戏加载时间；恢复只获得有限观察/清理预算，不重置执行截止。同步 Lua 或清理回调堵住游戏线程时，pcall、C_Timer 和宿主超时都不能保证强制中止；本方案不宣称已提供任意 Lua 抢占或沙箱。skill 要求有界循环、分批执行和清理注册。

探针的完成请求与结果封存分开：同步入口返回或受管异步回调正常退出后，Runner 才确认结果。Finish/Fail 在当前调用栈中只申请结束，不立即发布最终报告；同一栈在 Finish 后抛错必须覆盖候选成功，重复或晚到完成不能改写已封存结果。异步入口由 Runner 的小型回调包装统一捕获异常、检查 operation/runtime 归属，并在任务终结后拒绝再次进入用户回调；不能只在 Finish 时检查，因为回调在此之前就可能修改游戏。未经包装的任意定时器、事件或全局修改不在这个保证范围，skill 和输出必须如实说明。包装接口及 Finish 返回语义随新协议一起冻结，不能静默套到旧脚本。

## 3. 四个模块，一个业务权威

```text
CLI / skill ───→ Target（目标与能力）
       └──────→ Investigation（完整调查与恢复）
                         ├──→ Transport（命令投递）
                         └──→ Evidence（观察、验证与归档）

工作台 / 接收窗口 / 二维码 = 对上述事实的展示
```

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| Target | 安装身份、进程/窗口、角色、build、协议能力及当前可操作性 | 调查阶段、业务成功 |
| Investigation | 冻结意图、唯一任务记录、资源占用、完整执行和恢复 | 按键细节、字体、二维码绘制 |
| Transport | 唤醒、接收、摘要校验、提交、有限输入预算 | 判断业务完成、ACK、业务清理 |
| Evidence | 读取光学/SV证据、严格关联、报告校验、归档 | 推测没有证据的成功或授予输入权限 |

沿用一个 operation journal 保存业务权威，不再外包一套“主状态机”。投递尝试是 operation 下的诊断证据，不能再成为 Agent 必须逐个关闭的第二套任务。首连没有业务 operation，其短时投递记录仍须保存未知输入证据，但公共 connect 输出负责组织恢复动作。

每个结论只有一处负责：游戏 Runner 确认执行和受管资源事实；Transport 记录实际投递及未知边界；Evidence 校验报告与光学/SV来源；Investigation 依据这些证据计算 complete 和下一步。ready、投递成功、报告存在、资源已释放是不同事实，任何一个都不能冒充其余事实。CLI、skill、UI不再各存一份“当前阶段”；恢复与首次执行调用同一推进实现，不建立修补用的平行恢复链。

判断设计是否仍然简洁：新增失败场景原则上只增加现有事实的取证/处理和回归用例，不新增一条 Agent 必须学习的底层命令。不新增后台 daemon、全局当前窗口、第二份完成状态或无归属的万能 reset。模块内实现可以有私有细分，公开接口不暴露这些细分。

游戏端保有真实运行事实，宿主 journal 不能凭阶段推测这些事实。新增业务观察接口，携带 operation/request、代码摘要、session/runtime 和新 challenge，返回当前事实或明确 unknown；只重呈现事实，不调用 run/load/reload、不重置预算、不创建替代业务。status 只读宿主，resume 才可在授权和同一 owner 下调用游戏观察。观察入口必须能在普通业务回执已丢失时工作，不能先要求找到那张旧回执才能读取它。

UI 关闭、切页、隐藏二维码、取消输入只改变相应展示或输入资源。它们不能隐式 ACK、完成或取消已经提交的业务。

## 4. 目标身份与多 build

严格区分四层事实：

1. **安装**：规范化实际路径、产品 flavor、磁盘完整 build、受管 addon 版本与文件摘要。
2. **运行实例**：PID + 进程启动时间 + HWND + 可执行文件身份；同一个安装可以有多个实例。
3. **游戏身份**：实际运行 build、角色 GUID、角色/服务器、声明并验证的协议能力。
4. **当前就绪证据**：runtime epoch、序列和新鲜度；reload 后这层允许变化，不能误认为角色/实例已变。

目标在任务创建后固定。PID 被重用、角色更换、客户端重启或 build 不一致时停止输入；不能把原任务自动迁移到新进程。正常 reload 保留目标，通过原任务相关证据更新就绪代际。

目录名只是位置；flavor/version 元数据和游戏实测身份要匹配。Retail、Classic、Titan 分别验收；Forever 保留代码但在完成对应真机验收前不宣称支持达到同等标准。客户端 API 差异集中在 Compat 和客户端目录。

source commit、data build、hotfix capture 和 live build 分别固定，不能压成一个含糊的“版本”。查询缓存必须覆盖其实际输入：源码 commit/分析环境、数据 build/定义/locale/overlay/解密上下文。Live 自动关联 data/source 时只能采用明确匹配的固定引用；不匹配必须显示原因。

## 5. 多实例与共享资源

用具体资源决定是否并行，不用全局“当前游戏”或整个工作区大锁。

| 资源 | 规则 |
| --- | --- |
| 一个窗口 | 同时一个完整调查；占用一直到该任务要求的收尾完成，或显式 abandon |
| 一个 operation | 同时一个驱动者；多个 CLI 的 status 可读，同任务 resume 不得双执行 |
| 同一安装的插件文件/队列 | 跨工作区协调；更新、发布与撤销原子化，只修改精确条目 |
| 同一报告文件 | 按实际存储位置协调；不能仅因 HWND 不同就认定安全 |
| 不同安装/独立报告位置 | 可以并行，失败和超时互不阻塞 |

队列方案：保留一个有容量限制的共享队列清单，每条记录携带不可变操作和目标身份；原子合并/精确删除，不能整文件覆盖他人的条目。与实例相关的运行许可必须由所选窗口握手授予，其他实例加载同一份队列不获得执行权。安装升级不能趁未决任务仍依赖旧协议时覆盖它的运行环境。

队列原子合并和精确删除在现有 delivery 已有实现，本轮复用并验证，不另建队列框架。保留现有容量合同（16条、单条256 KiB、总源1 MiB）及协议/报告/日志上限；容量用尽返回结构化原因，不驱逐未决操作。新字段必须通过最坏长度、QR容量及全部客户端的编解码验收。

**报告存储需要解决当前账号级共享文件的问题。** 当前 TOC 的 LycheeToolkitDB 是账号级 SV。拟将桥的会话恢复信息、任务回执和报告移到独立的角色级 SV；账号级设置保持设置用途。宿主按 installation/account/realm/character 定位，再校验 GUID、operation、build、nonce 和正文摘要。仅按账号加宿主锁不能阻止另一个游戏进程自行保存账号 SV，不能把这种锁包装成数据隔离。

不同角色拟使用不同报告文件；角色级路径、首次写盘、账号映射和重入必须先实测。宿主串行调查不能阻止另一个同路径游戏实例自行写 SV。同一实际报告位置有多个可观察写入者时，在副作用前拒绝需要可靠持久化的新调查，不能仅通过串行任务宣称隔离；未知写入者是显式边界。对任意游戏进程覆盖磁盘或游戏崩溃，不承诺报告永不丢失；承诺缺失/污染不会被接受成正确结果，已归档报告不受之后覆盖影响。

角色级桥状态采用独立根和 schema，明确包含报告、重入信息、运行代际及必要的终结凭据；账号级 options/history/exports 不自动迁移。必须同时变更 TOC/安装校验、Persistence、Session/Reentry、报告路径选择和受限解析器，不是单改 TOC。旧当前产品证据按原格式只读核验；新协议不接管旧未决执行，不读取已退役产品数据。

占用分两种：短时 OS 执行锁阻止同时驱动；持久占用记录保留未决工作的责任。进程退出只释放前者，不自动清除后者。冲突输出实际 owner operation/workspace，不能无条件抢占。

首连/主动识别同样要取得跨工作区窗口 claim；任务内 reconnect、观察和收尾借用原 owner。准入先以本地原子/CAS提交保存不可变意图、源快照与请求索引，此时尚无输入许可，也不占共享窗口。取得短时准入锁后重检幂等、安装维护和既有 owner，原子发布引用该意图摘要的共享 claim，再提交本地准入事实；所有步骤完成前不修改队列、不输入游戏。不能先发布只有 operation ID 的共享占用，再首次保存该任务正文。

中断恢复规则明确：只有本地意图时重新竞争准入；本地意图加同 owner/摘要的 claim 时补完准入；别人的 claim 存在时返回实际冲突，不抢占。本地意图丢失或 claim 损坏不凭 PID 已退出自动删除，而是保留证据并给出明确修复阻塞。正常崩溃路径不应生成“没有任务正文却永久占用”的孤儿记录。共享 claim 在协调锁内以完整临时文件、同步和原子发布落地，不直接暴露半截 JSON；文件系统损坏仍属显式限制。

资源顺序固定为短时安装准入/维护检查 → 窗口及报告位置驱动权 → 短时 metadata提交；不持有全局 metadata写事务等待游戏。后续队列文件更新仅持短时安装文件锁；升级持维护标记拒绝新准入，发现依赖该安装的未决 owner 则拒绝替换，避免持大锁等其完成。共享 marker与本地journal不是一个原子文件系统事务，必须测试每个中断点的同 owner 恢复。

宿主占用已释放不等于游戏可接受新业务。每次新任务准入还要取得当前 runtime 的肯定观察：没有未终结探针及未释放的受管资源。abandon 只退役宿主责任和精确磁盘条目；Queue.Reset、Session.Release/Bind 或队列为空都不能证明旧回调已停止，游戏端任务事实不得因重连而被抹掉。旧执行未知时，仅允许在精确目标和新驱动权下取证或执行已有授权的恢复 reload；直到确认旧任务受管资源已释放，或验证新的 Lua runtime，才允许新业务。旧任务仍保留 abandoned/执行未知，reload 不追认它成功，也不撤销它已经产生的持久副作用。

## 6. 接收器：短时输入事务

```text
空闲 → 接收 → 摘要确认 → 相关提交 → 释放输入 → 交给业务执行
```

- 首次 identify/connect 也使用同一个专用接收窗口。
- 用户已批准默认唤醒入口。明确基础成本为5个frame、3条runtime override；正常登录后无常驻事件/OnUpdate/hook/timer。其余opt-in业务继续禁用零资源；延迟登录与战斗恢复只订阅必要事件，完成后撤销。完整TOC和绑定测试已覆盖这个成本，不再声称首次 /dev 前绝对零frame。
- 接收开始后才创建模态输入资源；在游戏事件循环可响应时有独立截止、失焦/战斗/离开世界清理，构造异常同样释放焦点和遮罩。游戏线程卡死时不声称计时器仍能强制解锁。
- 先收完整报文，再读回长度/摘要，再通过 nonce + epoch + attempt + challenge 确认提交。
- **提交后立即释放输入状态，再调用业务。取消按钮、Close 和 accepted QR 都不是下一次命令的前提。**
- 不在正常链路加入 receiver_closed、解封回执或关闭后的业务回执恢复。
- 明确提交前拒绝可以有限重传。提交后先核对同一个 operation；任意代码执行和 reload 的未知结果不能重放。观察、精确 ACK/终结等由业务定义的幂等动词，可在同一 owner 和相关凭据下有限重试，不与“重新执行探针”混为一谈。
- 运行时去重与输入框生命周期分离；新唤醒、换页、二维码被替换不能清除重放保护。
- 先校验协议能力，再发送内容。协议不匹配返回需要激活哪一版，不能因为产品版本号相同就继续。

Ctrl+Alt+] 唤醒、Ctrl+Alt+Shift+] 校验提交、Ctrl+Alt+[ 紧急释放继续保留。自定义快捷键必须验证真实生效，不覆盖用户自己的账号绑定。引导成本已同步 design.md；模拟与真机成本证据分别记录。

只有证明旧 attempt 未越过持久 commit 边界且新接收环境已重置，恢复才可在原 operation 内重开接收；缺少这个证明继续 unresolved。每条 input前的意图持久化失败则禁止发送；发送前设置观察下界并保留捕获流，不能在发送返回后才建立 fence，丢掉唯一有效帧。

## 7. 报告、二维码与完成

QR 只携带必要的身份、能力、提交摘要和阶段凭据；完整报告走 SV，再由宿主复制到不可变 evidence。QR 不承载整份对象树或报告，也不决定业务状态。每次等待都要求正确目标和操作关联，不能把旧截图刷新成新权限。

SV 的真实写盘点是 reload/logout，方案保留必要的持久化步骤。不能承诺提交后直接读取最新 SV。报告已在内存但尚未落盘时，要显示真实阶段。

完整调查的完成条件：

```text
已验证的终局结果（成功/失败报告，或最小终局错误凭据）
  + 本任务受管探针资源已释放
  + 精确 ACK / 队列条目退役
  + 本任务显示收尾已验证
  + 释放本任务占用
```

其中 ACK 与报告可以先完成；若显示清理失败，报告仍可用，`complete=false` 并指出剩余清理。完整任务必须持有窗口直到显示收尾结束；禁止先释放窗口，再用不带任务归属的 hide 清掉可能属于下一任务的显示。现有 cleaned 自动释放的实现不满足该目标，不能只将现有原子命令串起来。只有一个 goal决定何时终结，不再叠一份独立 completion状态机。

采用归属明确的终结接口：内部清理显式带 operation 身份及本任务终局凭据，拒绝操作他人的回执；观察并归档清理证据后再释放占用。它使用原 owner，不经过“所有占用窗口一律拒绝”的独立 hide路径。释放共享占用中断时，业务不重跑，仅恢复释放；释放尚未确认，完整任务保持 complete=false。完成后的重试不发送游戏输入。旧原子 `ack` 保留旧的完成范围；它不能改变完整调查最初承诺的收尾范围。

语法/运行错误、明确拒绝、报告编码/secret/容量失败，必须有可关联的终局错误和针对该终局的精确收尾；没有正文时 report=unavailable，不伪装为 verified。只有执行效果未知才进入 unresolved。连接或独立 reload 按自身目标完成，不要求 probe 报告。用户关闭窗口不是任意 Lua 的安全取消机制。

Runner 先关闭该任务的受管回调入口，记录执行结果，逐一运行已注册的有界清理，再封存包含执行与资源清理事实的报告；一项清理抛错仍继续其余清理，并保留有界、secret-safe 的错误。任务结果已知而资源未释放时，报告仍可验证，整体 complete=false，明确缺少的是资源清理。队列退役、QR隐藏不能冒充资源释放。任意 OnCleanup 回调不假定幂等，不在 resume 中盲目重放；返回有前提的恢复动作或阻塞，必要时通过已授权且已验证的新 runtime 结束旧资源，不改写原清理错误。业务结果、受管资源、桥/显示收尾是同一 operation 的不同事实，不另建并列任务。任意脚本的外部/持久副作用不属于可自动回滚资源。

“未解出二维码”只是观察，不能独自证明清理。终结先取得业务肯定凭据并保存有界 tombstone，再观察该任务展示及短时控制回执结束。目标、时间下界、完整显示区域和捕获有效性须匹配；ROI漏码、遮挡、缩放/解码不确定均不能升级 cleared。物理显示观察不替代逻辑 ACK；具体终结回执与显示结束的无循环协议由 G2 实验证明，不增加正常输入的 receiver-close解封事务。

终局最小记录拟按每 runtime 16 槽、每槽编码上限2 KiB、合计32 KiB保留，执行前预留所需槽位；未确认宿主已归档的证据不得因新任务到来被淘汰。已确认记录的回收不能恢复旧执行许可：执行还须匹配当前任务授权和 runtime，旧 operation、旧 attempt 无权重新执行。容量耗尽在新副作用之前明确拒绝，不在执行完成之后才发现连最小失败凭据都无处保存。最长身份/错误字段必须能装入上述预算，退休条件和跨 reload 保留须由 G2/G3 的容量反例证明；若装不下先修订共同协议合同，不偷偷放宽单端限制。

Agent 输出保留 result.v1，主要字段是 operationId、target、report、business、cleanup、display、complete 和结构化 nextAction。投递次数、按键和协议字节放在可展开证据里。

complete 表示本命令承诺的工作已终结和收尾，不表示断言成功。新完整任务的 execute/resume 在可验证失败且收尾完成时返回 business=failed/assertion_failed、complete=true，并使用既有 exit 5 类别；待证据/待清理 exit 6；宿主取消 exit 7 不声称游戏已取消。旧原子命令的退出合同不随这一新增入口静默改变。只读 status 的 exit 0 表示查询成功，不能替代结果里的 complete。nextAction 包含原因和前提，不是对所有 pending 无条件建议无限 resume。

## 8. 失败恢复与绝对 reload

| 故障 | 系统行为 |
| --- | --- |
| 提交前格式错误 | 有界重传，超过预算给出明确原因 |
| 提交消息部分送达/结果未知 | 保留提交意图，读取原任务结果；不重放 |
| 已有报告但 ACK 失败 | 返回报告，同时保留精确 ACK 义务 |
| ACK 完成但显示清理失败 | 仅恢复本任务显示清理，不再次运行 |
| CLI 退出 | 新进程读同一 operation，取得驱动锁后恢复 |
| 进程、角色或 build 变化 | 停止输入，保存原目标和原证据 |
| 执行错误 | 返回已验证的业务失败，不伪装成传输失败 |
| 明确 abandon | 保存未知执行事实，退役宿主占用；新业务仍须验证游戏空闲或新 runtime |

绝对 reload 保留固定 Esc×3 → 聊天框 → /reload 的独立兜底路径，绕开失效接收器；仍必须核对精确窗口、安装版本和占用，提前记录意图。没有相关结果时标记未知；不能将 fallback 放进所有超时的自动重试循环。激活新安装或已有授权的恢复任务可以自动使用，普通业务失败不借它扩大副作用。

## 9. UI 与 skill

按 Impeccable 的原生游戏界面约束设计，先定布局和组件，再实现所有页面。

- 工作台：常驻左侧导航，右侧唯一工作区，设置在侧栏底部；顶部只放当前页面与必要操作。合理默认尺寸、可调整空间；通常尺寸不靠横向滚动使用。
- 八类本地工作台能力无需 CLI 连接：运行/历史/复制、对象搜索拾取导出、事件监听详情、函数追踪、BugGrabber诊断、导出记录、自动化任务、关于。UI动作用同一游戏业务接口和owner仲裁，不另造执行状态；有CLI未决任务时，冲突动作明确拒绝或进入已定义的中断流程，不能随手清掉它的报告/会话。
- 阅读：正文 14–16、元数据不低于 13，标题有层次，支持 UI scale；不靠缩小全界面解决拥挤。
- 控件：统一圆角、字段、按钮、开关、焦点、禁用和错误状态；圆角必须实际绘制，不能仅写入设计文档。
- 设置：短行分组；快捷键显示人可读组合，交互采用受限按键录入与统一保存/重置反馈，协议编码留在内部。避免三个大输入框加三个零散“应用”。
- 接收窗口：紧凑状态面板，只展示“接收/校验/交给游戏”和紧急退出；真实 EditBox 作为输入设施，协议字符不铺满玩家界面。
- 自动化：优先展示任务目的、结果和待恢复原因；长 OP ID、哈希和协议字段折叠到详情。
- 二维码：独立左上角光学通道，按载荷精简、整数模块和可读边界定尺寸；不能裁圆角或任意缩小损害解码。

skill 默认：明确目标 → execute → 检查 report/business/complete → 按有前提的 nextAction 恢复原 operation。不得停在二维码出现或仅 report verified。每次调用和自动恢复均有界；外部条件不变且没有新证据时返回明确阻塞，不无限重试。多目标按目标分别建立任务，不让 Agent 手动串接 receiver、flush、ACK 等实现细节。授权边界沿用当前会话，避免机械重复确认；未知业务仍不盲重放。connect-only、独立reload、内建bugs有各自完成条件。

## 11. 实施顺序与验收

以下为实施顺序概览；逐项不变量、独立判定依据、故障注入点、预算、三客户端证据与发布阻断均以配套 [可靠性验收合同](agent-live-acceptance-2026-09-27.md)核对。现有 regression.md 的能力矩阵继续适用，不能用本轮集中验收替代 source/data/assets 与工作台回归。

1. **方案冻结前置门槛**：G1明确引导成本合同；G2验证持有owner的恢复观察/终结/清屏无循环；G3实测角色级SV及混合版本；G4并发准入和崩溃故障注入。先完成小范围证据实验，不以全套重写赌这些前提。通过后更新权威合同并冻结接口。
2. **失败用例先行**：真实投递接口与业务接口的故障注入，覆盖重复/部分输入、唯一新帧、二维码替换和多实例资源冲突。
3. **核心纵向切片**：先让一个 execute 从连接到全部收尾跑通，resume 用同一实现；删除 accepted-seal/关闭事务，不同时保留两套权威路径。
4. **多实例存储和升级**：角色级报告、共享队列条目、跨工作区占用、协议激活及旧未决任务的证据保留。不能把旧未知任务解释为新协议成功。
5. **UI 与 skill**：按稳定模型重做页面与编排，统一中英文、字号、圆角、空态、错误和恢复入口。
6. **完整回归与真机验收**：离线通过后才受管安装、必要 reload、WGC 测试；随后才讨论发布。

必须验收的用例：

- 全新安装、已禁用业务功能、首次唤醒/连接、升级和正常 reload。
- 连续任务不需人工关闭输入框；业务立即换二维码也能完成。
- 每个提交/落盘/ACK/清理边界中断，恢复不会重复执行。
- 提交后唯一回执帧、回执被覆盖、执行预算过期但报告已存在；观察可恢复且不重置执行截止。
- 完成后同 key 重试零输入；改变不可变输入立即冲突。
- 两个 CLI/工作区争同窗口；同一目标只一个驱动。
- 两个全新workspace并发首连、同key并发查不到、安装维护与新准入竞争。
- 本地意图提交前后、共享claim原子发布前后、本地准入提交前后分别崩溃；同owner可恢复，失败步骤不留下无正文的永久占用，不提前输入或修改队列。
- 同安装双窗口、不同角色、不同账号；独立位置并行；同一游戏写入者上的多个CLI串行，存在其他同文件游戏写入者时明确拒绝可靠持久化调查。
- 同报告位置存在第二游戏写入者时不能把宿主串行化当成已隔离；新旧SV、旧runtime/新磁盘、未知schema及首次写盘。
- 两个目标同时报告和 reload，不串码、不替换队列、不删除对方条目。
- PID 重用、同名角色、build 不符、一个窗口战斗/最小化/黑帧不影响另一个候选。
- 清屏与新任务并发，不清掉新回执；完整任务收尾前不释放窗口。
- 遮挡、ROI漏码、缩放、黑帧、码解不出都不单独证明清屏；终结凭据丢失可查询。
- 已知语法/运行/报告编码失败能准确收尾；未知执行不伪装失败已收尾。
- 删除原脚本、变更probe名称、窗口改标题不影响按operation恢复；参数/actor/build变化不能绕过幂等约束。
- 同步阻塞、晚Async、超时后晚Finish、清理异常；只在游戏线程可响应时验证协作式超时。
- Finish后同栈抛错不能保留成功终局；受管回调结束后才封存，晚到受管回调在执行用户代码前被拒绝。
- 清理回调抛错、重复/递归Finish、清理期间会话改变；错误可见，其余清理仍执行，未释放资源不算complete，不自动重跑未知清理副作用。
- abandon后旧定时器/事件仍存活、Reset后Busy=false、重连丢失内存索引；这些都不能单独放行新业务，受管资源释放或已验证的新runtime才可解除阻塞。
- 8个工作台页面和接收框，中英文、不同缩放、长文本、空状态、键盘焦点与异常构造。
- source/data/assets 原有场景回归；不同版本缓存、schema、hotfix和语义环境不串用。

自动化验证执行 build/vet、受影响包测试与强制 Lua 5.1 全套。真机按 Retail/Classic/Titan 单独记录 before/after WGC 图和结果证据；没有在线客户端的行保留 not_run。完成本方案的依据是上述场景结果，不是测试数量或“0错误率”承诺。
