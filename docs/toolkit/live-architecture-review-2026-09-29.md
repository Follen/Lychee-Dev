# Live 方案复审：先固定保证，再选择协议

2026-09-29；审查对象为同目录的 live-architecture-proposal 与槽位前置实验。
主 Agent 核对代码及一手资料，三个子 Agent 分别独立审查协议、生命周期和 Skill。
本轮只修改设计文档；未实现候选协议，未操作游戏。以下代码位置以本工作树为准。

## 审计结论

现版不能直接按“架构已定”实施。主机职责划分可以采用；共享槽位协议仍需原型准入。
推荐保持小型单体：每实例一个持久执行负责人，依据目标和证据推进；底层提供观察、
发布与单次输入；共享资源按实例限额并预留恢复容量。复用现有存储、OS 锁和 Lua 执行器。
不增加常驻服务、消息中间件、通用工作流引擎或另一套事件数据库。

“业界最优”不是某个架构名字。这里的选择标准是：不串目标、不重复未知副作用、
一个实例的故障不吃掉其他已接纳实例的资源、有界停止、代码与运维成本可控。
同安装本来就共享磁盘和文件，桌面也共享输入；不能承诺它们发生全局故障时完全隔离。

## 必须修正的发现

### P1：关闭仍可能执行新业务，且依赖新绑定

证据：`internal/live/channel/wait.go:65` 在 closing 但不 quiescent 时仍可到 Run；
`driver.go:283`、`:313` 会 prepare/commit。`recovery.go:48` 先 Connect 才 Supersede。
旧方案 §15 也先要求换代绑定，后处理 close；slot 1 被挡时会连关闭一起阻塞。

修正：先接纳停止目标，再按已有副作用证据选择收尾。不得为了完成 disconnect 发送新业务。
尚未发布 prepare 可本地结束；prepare 已接受且没有发布 commit 时，v1 unbind 仍会
因 pending 拒绝（`addon/Bridge/SlotProtocol.lua:151`），只能使用已授权且可验证的
reload/销毁路径或明确阻塞。commit 一旦可能被读取，即使没有本次发键也保留 unknown。
进程确实退出时直接精确退役，不为关闭创建新绑定。活进程的最小销毁证明尚未独立实现，
不能在设计中把它当现成功能；必要 fresh bind 被挡时诚实返回关闭未完成。

### P1：多封套解决占位循环，不自动提供故障隔离

生产发布/日志路径的 slot 1 循环已离线复现；参见
[前置实验](slot-concurrency-feasibility-2026-09-29.md)。但集合仍可能被一个反复失败的
实例填满。仅设一个全局成员数上限，会把“占一个槽”换成“占满集合”。

修正：按固定实例生命周期接纳并分配份额，reload/新 CON 不能刷新该份额。
普通业务和恢复分别保留成员与字节预算；未知成员消耗所属实例额度，不能挤占别人。
接纳新实例之前即核验容量。超过声明实例数/故障次数，明确拒绝；不按 TTL 删除未知请求。
共享文件合并与校验失败、磁盘错误仍是共享故障，不能用逻辑配额宣称物理隔离。

### P1：集合路由身份和一次性读取还没有证明

`SlotRuntime.lua:33`–`:39` 的 token 来自持久 epoch、时钟和随机数，并非 OS 实例 ID；
主机知道 PID 不代表 Lua 能核验 PID。拒绝已发现的同 runtime/不同 consumer 冲突是必要
措施，但不足以证明未知实例不会具有相同路由身份。初绑挑战必须在固定进程验证；
路由歧义不得发业务。需要定义碰撞模型、接纳时核验与可接收身份，不能宣称绝对唯一。

`SlotRuntime.lua:77` 的 wake 仍读取 nextSlot；迟到键可能消费后续槽。
已有实测证明 LoD 加载一次后不重读磁盘。集合 loader 必须把加载但无匹配、歧义、
格式错误等情况记为该物理槽已耗用并可观测，不能等待在原槽补写。
这需要协议原型，而非单纯更换 Payload.lua 数据格式。

### P1：请求去重范围没有说清

`internal/live/channel/request.go:22` 与 `project_windows.go:445` 在指定 CON 日志中查
request key。新 CON 传同 key 不提供跨连接去重；跨 runtime 也没有任意业务恰好一次保证。

最小决策：保留 `(项目, CON, request key)` 的现有范围和内容冲突检查。恢复沿原 CON、
原操作；runtime 换代不创建新业务身份。新建 CON 是新连接，不是恢复未知请求的捷径。
暂不引入项目级请求服务。若后续产品要求跨 CON 接管，必须明确迁移同一规范操作记录，
由所有入口共同执行去重，不能靠 Skill 记住 key 代替代码保证。

### P1：预算与取消还不是完整合同

`internal/command/live_channel_windows.go:36`–`:40` 每次创建新等待预算；
`wait.go:20`、`:54` 将上下文结束投影为 pending。停止等待不等于游戏停止。

修正：业务请求、显式 reload、首次 close 各有一次初始化的持久自动推进预算。
相同目标的 resume、重复 close 和 CLI 重启共用它；不能换请求名给同一关闭目标续期。
业务预算不足不吃掉预留的收尾预算。时钟异常保守停止自动动作；读取已有证据仍可进行。
用户停止只阻止新的业务提交并安排有界收尾；不能撤销已经发布/执行的 commit。

### P2：不能把现有 fence 和清理标记说得比实现更强

`driver.go:125` 的 fence 为 1；当前依赖 OS 实例互斥、持久 owner、准确请求及禁止未知
重发，不是可超时接管的分布式租约。保留不抢占的 OS 锁；只有未来增加接管时才需要
设计递增代际和接收端拒绝旧 writer。不要为套用 fencing 模式额外制造接管需求。

`ProbeExecution.lua:16`、`:28` 的清理执行一次，失败后不自动重复；
`SlotProtocol.lua:142` 因资源未释放拒绝 release。保留清理失败为准确义务，取回报告
不以清理成功为前提；runtime 销毁只证明旧执行环境结束，不证明业务状态/第三方 UI 恢复。

### P2：方案前后矛盾会导致错误实施

旧稿开头和 §7 承诺不改协议，§18 又把协议候选加入范围；§13 声称消除卡死结构，
而 §18 已确认 v1 恢复闭环。主稿已收紧为主机整改与协议原型两条验收线。
不把“更多 pending 原因”当成活性修复，也不把诊断测试 PASS 当缺陷已修好。

## 方案比较与选择

| 选项 | 当前需求下的判断 |
| --- | --- |
| 主机收敛，保留单请求物理槽 | 必做基础改进；不能解决已复现的同槽阻塞闭环 |
| 有界集合＋每实例配额＋恢复预留 | 支持现有同安装多实例的首选原型；通过身份、耗槽、崩溃及容量门槛后才采用 |
| 每实例独立安装/槽位文件 | 消除共享文件争用最直接；改变部署和启动方式，仍共享桌面输入；作为强隔离可选部署，不强迫用户迁移 |
| 每实例固定槽区或邮箱 | 当前 nextSlot 与初绑身份不支持直接分区；需要新分配/寻址协议，不能只按 PID 取模 |
| 独立可寻址控制通道 | 若实证可行，能减少控制依赖；目前没有验证过的路径，不凭空承诺 |
| daemon、队列服务、通用工作流引擎 | 不能让一次性 LoD 重读或让未知副作用自动可重试；当前增加运维与状态来源，不采用 |

候选集合的容量规格必须在原型中冻结。设最多接纳 N 个实例，每实例在一个物理槽允许
D 个业务成员、R 个恢复成员，单成员最大字节 E，物理集合预算至少容纳
`N × (D + R) × E + 编码开销`；还要满足实际 Lua/文件上限。R 必须涵盖所声明故障模型
内最坏控制序列及未知尝试，不能随手取 1。额度不足时拒绝接纳；A 无论如何换 runtime
都不能消耗 B 的份额。N/D/R/E 的取值和性能尚未验证，不写假数字。

## 采用的一手设计依据与适用范围

- [Kubernetes Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)：目标与
  当前事实分开，由负责人推进。这里只借用协调原则，采用命令期间有界推进；不搬入集群、
  常驻循环或多控制器框架。
- [AWS：幂等请求](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：
  请求身份、参数一致性与迟到请求必须明确。我们的按键不是可携带请求 ID 的可靠 RPC，
  因而不能据此开启自动重发或宣称跨 runtime exactly-once。
- [Azure Bulkhead](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead)：
  故障隔离要落实到资源分配，而不仅是释放短锁。这里据此提出每实例额度与恢复预留；
  该资料不证明 WoW 集合协议可行。
- [AWS：限制重试](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html)：
  重试要有单一负责人和上限。CLI 管准确资格与持久预算，Skill 不再自行补一层重试。
- [Kleppmann：锁与 fencing](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)：
  旧执行者是否被资源端拒绝，比“拿过锁”更重要。当前是本机 OS 排他，保留其适用模型；
  本文不由分布式锁的限制推断现有 OS 锁已失效。

以上是设计依据；推荐组合及对本项目的取舍是本次审计判断，不是外部资料对本项目的认证。

## 验收先后顺序

1. 冻结关闭行为、请求范围、预算归属和 blocker 合同。用公开入口验证 stop 不启动业务，
   首绑/reload 任意阶段都能观察现实；公开恢复失败返回真实条件。
2. 隔离原型仅实现同槽 A/B/C 集合：身份歧义、无匹配耗槽、迟到键、满容量、单边连续
   reload、崩溃前后合并/删成员、晚到回执。失败时回到协议选择，不扩写主机状态补偿。
3. 原型通过才迁移 Go/Lua 协议、安装和日志版本；保留旧未知事务的可恢复路径，禁止
   同安装旧 loader 读取新格式。每迁移一个职责同步删除旧决策入口。
4. 强制 Lua 全量测试、公开 CLI 故障序列、Retail/Classic/Titan 分别实测，包含 first-install、
   upgrade、reload、relogin、同/异安装与同/异 build。Forever 单列实验，不继承验收。
5. 同条件比较扫描量、锁时间、集合大小、CPU/内存、请求耗时与日志增长；Skill 用真实行为
   场景评估，不用关键词测试。固定目标不变、无二次 writer、无预算续期、unknown 不误报。

本轮新增发现来自静态审计；slot 1 循环沿用前轮离线实证。没有新增运行测试或实机证据。
修订稿可作为下一步原型与主机整改依据，尚不能作为完整健壮性验收结论。
