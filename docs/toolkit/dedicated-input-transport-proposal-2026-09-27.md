# 专用输入框传输方案

日期：2026-09-27。状态：原始设计提案；工作区实现追踪见总方案与实施状态，生产真机验收未据此完成。

目标：以荔枝风格的专用输入框替代聊天框承载机器命令。默认唤醒键为 Ctrl+Alt+]，提交键为 Ctrl+Alt+Shift+]，关闭键为 Ctrl+Alt+[；CLI 完成唤醒、确认、输入、提交和结果读取，正常链路不依赖 Computer Use。接收期间普通 Esc、Enter、Tab 和鼠标操作均不提交、不关闭、不向游戏下层传播。

本次用户确认：基础入口不依赖桥已连接，connect 本身也从此输入；短回执配合完整 SV 报告，不建设通用无 reload 快速通道；Agent 声明执行预算；正式接入前先做独立测试插件/宿主脚本。安装激活及桥失联另有固定 `Esc × 3 → Enter → /reload → Enter` 原生兜底。独立 Retail 回显实验已通过，工作区实现继续以实际代码和测试核对，其他客户端与生产全链仍待验。

本方案早期的“提交后即 accepted”已由正式双段提交修订：`LDB1` 严格暂存与读回后投递物理提交键，插件发 `receiver_commit_ready` challenge，CLI 再发关联 nonce、attempt、challenge、正文摘要的 `LDC1`，精确匹配后才 dispatch。迟到的旧物理提交键不能提交新的 stage。关闭键仅释放接收器，不是业务取消或 ACK。绑定配置、冲突检测、CLI 首连 `--wake-binding` 和 ready 生效值回报已有工作区实现；各客户端实际验收仍待进行。

## 1. WoW 是否支持 Ctrl+Alt+]

支持这种“两个修饰键＋一个普通键”的绑定形式。固定正式服源码提交 `09b9db7948abc9b9648dedaab51eb0cf3ee67b31` 中：

- `Blizzard_SharedXML/KeyCommand.lua` 的 GetBindingFullInput 分别检测 Alt、Ctrl、Shift、Meta，最后追加普通键；注释规定前缀顺序为 ALT、CTRL、SHIFT、META。
- `Blizzard_SharedXML/BindingUtil.lua` 的 CreateKeyChordStringUsingMetaKeyState 采用相同顺序；绑定忽略列表不包含右方括号。
- `Blizzard_Settings_Shared/Blizzard_Keybindings.lua` 使用上述组合结果调用 SetBinding。

因此显示文案可以写 **Ctrl+Alt+]**，内部规范键字符串为 **`ALT-CTRL-]`**。

本次将真实 KeyCommand.lua 加载到离线 Lua 5.1，用 Alt=true、Ctrl=true、Shift=false、Meta=false 调用 GetBindingFullInput(']')，输出并断言：

```text
Pinned WoW GetBindingFullInput: ALT-CTRL-]
```

这是源码和离线规范化检查，不是实际注册绑定、不同键盘布局或 CLI 投递成功的真机证明。Classic、Titan 的对应基线仍需各自验证。

## 2. 接收界面

视觉与布局统一遵循项目根目录的 [Design.md](../../Design.md)，参考 Lychee 的近黑底、暖白文字、荔枝红强调和共享控件语义。该文档同时覆盖工作台重构，接收器不单独发展第二套样式。

二维码保持现有左上角 `TOPLEFT → UIParent.TOPLEFT (16, -16)`，独立于接收框及工作台；保留黑白颜色、四模块静区和现有模块尺寸规则。输入遮罩不染暗、不覆盖二维码，二维码不参加任何位移、缩放、淡入或 logo 动画。层级协调必须保证接收期间仍可读取，不能把协议回执嵌入新面板后随面板消失。

采用一个紧凑的荔枝风格窗口：荔枝 logo、标题“开发连接”、单行状态“正在接收命令…”。重传时显示“输入受干扰，正在重试（1/2）”。底部弱化显示剩余接收时间及 Ctrl+Alt+[ 关闭键。深色背景、荔枝色活动状态，默认不展示长串协议文本，不弹 tooltip。

真实 EditBox 保持可见、接收焦点并限制字符/字节数。上层可以用简洁的接收状态遮蔽复杂协议表现，但不能把实际接收控件隐藏后仍假定能输入。

打开期间使用插件自有的高层级模态背景，拦截落入该界面的鼠标操作；键盘由输入框和专用窗口接收，普通输入不继续传播到角色操作。这里的“独占”仅是短时游戏 UI 模态状态，不能承诺覆盖系统快捷键、操作系统切换、全部保护界面或其他插件主动抢焦点。

不用永久抢焦点的 OnUpdate，也不在失焦后与其他窗口循环争抢。意外失焦直接中止本次接收，发布明确状态。普通 Esc 被吞掉；Ctrl+Alt+[ 关闭接收器，不与唤醒/提交复用，并保留不可续期的硬超时。人工关闭不自动重新弹出。

## 3. 绑定与启用

- 唤醒入口随插件加载可用，不依赖 bridgeEnabled、session 或工作台打开。首次安装尚未连接、disconnect 后均可唤醒；identify/connect 使用同一个接收窗口。基础绑定声明/处理器与调查执行权限分离，唤醒不自动授权运行探针。完全禁用或未加载插件时由独立兜底重载处理安装激活。
- 接收窗口和调查资源按需创建；未连接仍保留最小唤醒注册，但不启动采集、轮询或自动执行。关闭窗口释放临时绑定、监听、计时器和焦点，有限隐藏控件可复用；基础入口成本单独计量。
- 在非战斗状态配置绑定。Ctrl+Alt+] 未被占用时作为默认值；冲突时不静默覆盖用户绑定。设置页或 `/dev receiver bind <wake|submit|close> <chord>` 可修改，`/dev receiver reset` 恢复默认值；设置页显示实际生效值。
- 插件使用可撤销的自有运行时 override，配置只保存到自身选项，不调用 SaveBindings 改写玩家账号键位。允许 `ALT-CTRL-`、可选 `SHIFT-` 加 `[`, `]` 或 `F1`..`F12`；wake、submit、close chord 不可相同，close 的末端按键还须与另两项不同。已有用户绑定冲突或实际 override 不生效时拒绝，具体 API/保护限制仍按各客户端验收。
- 唤醒键是幂等的 open：窗口已开时不关闭、不清空已有报文、不重置期限，不再使用 toggle 行为。
- 用户手动按热键与 CLI 唤醒进入相同接收器。热键本身没有执行任何探针或 Lua 的权限。
- 首次自定义唤醒由调用者通过 `--wake-binding <chord>` 传给 `live instances`、`live connect` 或 `live reset`；新 ready 回执携带三项实际生效值，CLI 核对并随 session 保存。首次默认唤醒失败时返回明确错误，不轮流猜测多个键、不退回聊天输入。
- 提交键规范名为 `ALT-CTRL-SHIFT-]`；关闭键为 `ALT-CTRL-[`。接收框获得焦点后仍须能识别唤醒、提交和关闭，不能只依赖可能被 EditBox 吞掉的全局绑定；入口复用同一命令处理器并防重复触发。具体识别路径需按客户端验证。

## 4. 一次命令的完整流程

1. **CLI 获取独占权。** 保留已有窗口、进程启动身份、角色及 operation 所有权检查；同一窗口一次只允许一个发送者。
2. **发送唤醒键。** 发送并释放自己的 Ctrl/Alt/右方括号，不立即盲输正文。失败后不发送任何正文。
3. **插件发布新接收回执。** 专用窗口显示并确认当前焦点确为其 EditBox，发布 `receiver_ready`，带接收器 nonce、runtime epoch、角色、协议版本、容量和有效期。CLI 要求来自本次唤醒之后的新画面，并排除已使用/已取消 nonce。
4. **CLI 输入有边界的报文。** 不输入聊天斜杠命令，不经 SlashCmdList 分发。报文包含协议版本、receiver nonce、operation/request ID、attempt ID、动作、参数、长度和校验值；使用受限 ASCII 编码，消除中文输入法对协议字符的需求。校验覆盖包括 nonce 在内的完整封包，另保留用于业务去重的稳定命令摘要。
5. **完整校验、读回后两段提交。** 插件检查完整性、nonce、有效期、角色、动作白名单及适用的操作归属，完整合法 LDB1 报文进入 staged，冻结这份不可变报文并丢弃后续普通字符，发布其长度、operation/request、attempt 和摘要。CLI 必须读回并与本地期望逐项一致，才发送专用物理提交键。插件此时只发布 `receiver_commit_ready` challenge，不执行业务；CLI 根据这份新回执发送 LDC1，其中 nonce、attempt、challenge、正文摘要必须精确匹配，插件再次核对前置条件后才进入 accepted 并 dispatch。失败发布固定字段的拒绝回执。Enter/Esc 永不提交，尚未 staged 的物理提交键与旧尝试迟到的物理提交键都不能执行新报文。
6. **结束输入独占。** 完整报文接受后关闭输入框、释放焦点和模态拦截，再推进实际业务。结果/执行状态使用独立回执展示，不能因输入框关闭而丢失。
7. **CLI 核验接收及结果。** 按 operation 和报文摘要确认 accepted，然后等待运行、报告、持久化及 ACK。accepted 仅证明报文被接受，不代表操作成功或永久落盘。

正文只传短小的机器动作，不把整个 Lua 探针塞进 EditBox。继续沿用已有受管队列加载已登记的不可变探针。初版可采用约 256 字节的报文上限和 20 秒接收硬期限作为设计起点；编码后的最长合法命令必须离线核算，容量或节奏不满足时调整合同，禁止静默截断。

输入完整性校验用于检测误输入和串扰，不是秘密认证。信任仍来自显式启用、目标绑定、操作归属、受管队列及精确结果关联。

## 5. 中断和恢复

| 情况 | 插件行为 | CLI 行为 |
| --- | --- | --- |
| 普通 Esc/Enter/Tab、鼠标点击或滚轮 | 在模态接收层吞掉，不提交、不关闭 | 保持既有有界接收事务，不因这些键重置期限 |
| Ctrl+Alt+[ 关闭 | 撤销当前接收、作废 nonce、关闭模态框 | 标记本次输入取消；已接受业务不因关闭而撤销 |
| 接收期限到期/CLI 退出 | 定时关闭并作废接收事务 | 保留输入进度，不假称执行成功 |
| 非预期失焦 | 中止接收，不持续抢焦点 | 返回 input_interrupted，停止剩余字符与提交键；不盲目重新抢焦点 |
| 提前按提交键、错误长度/校验 | 不执行；给出结构化拒绝结果 | 不以新 operation ID 重发业务；仅确认未接受时按下节有限重传 |
| 进入战斗、加载、离开世界 | 撤销未提交输入；后续受保护操作保持原有检查 | 等待明确可用条件；不盲目清屏或重载 |
| 已提交、接收回执未读到 | 保存当前 runtime 内的去重与接收结果 | 查询同一 operation，不直接重放执行 |
| 客户端重载/崩溃 | 旧接收 nonce 无效 | 重新核对 runtime；已有执行效果未知时保持 unresolved |

只清除本插件输入框内容，不清聊天草稿或其他 EditBox。结束时释放自有焦点；恢复先前输入焦点要检查目标仍存在、仍可见、环境未变，否则只释放，不向旧窗口发送按键。进入战斗时的清理必须走各客户端允许的路径，不能在保护边界上强行改绑定。

运行中的同步 Lua 无法靠关闭输入框抢占。合作式取消必须作为独立协议能力设计，不能把“接收取消”冒充“业务执行已取消”。

### 5.1 玩家夹杂输入：检测、整帧重传和去重

插件不能仅根据字符事件区分玩家和 CLI。字符白名单只能挡住部分输入，合法字符、删除、粘贴同样可能破坏报文。因此依靠完整性验证和提交前读回，不宣称能够只接收 agent 的字符。

接收器采用严格单帧解析：固定起止标记、长度、允许字段、nonce、attempt ID 和完整校验；容量溢出、非法编码、额外字符、缺字、换字均拒绝。不从混杂文本中扫描提取“看似正确”的子串，不纠正拼写，不猜命令。剪贴板修改、光标移动、选择/删除等编辑操作应在接收模式下拦截；即使某条路径漏拦，最终完整性检查仍必须生效。

完整合法帧一旦 staged，冻结输入快照。CLI 读回这份快照的摘要，再发专用提交键；后续玩家乱敲不会更改将要执行的内容。未获得 staged 回执时禁止提交。后台投递晚到的旧字符只会被当前帧校验拒绝或在冻结态丢弃，不得组成第二条可执行命令。

提交键本身不携带 nonce，原型必须补验旧尝试的迟到提交不会提交新 staged 帧；必要的提交关联机制在协议接入前确定。不能仅靠重复提交去重推断跨尝试安全。

自动纠错定义为**整帧重传**：

1. 接收器返回与本次 nonce/attempt 绑定的 rejected，明确 `accepted=false`。坏报文不能决定它自己的错误回执归属；关联身份使用接收器已有上下文。
2. CLI 停止剩余输入，不补交尾部或提交键。确认是可重传的输入完整性错误，而不是战斗、失焦、人工取消或执行错误。
3. 插件在下一次新接收尝试中清空自己的缓冲，生成新 receiver nonce/attempt；CLI 确认新 ready 后发送原始完整报文。operation ID 和业务内容保持不变。
4. 默认最多追加两次重传，即总共三次尝试；单次接收暂定 20 秒，整个重传流程暂定不超过 60 秒。间隔可采用 0.5 秒、1 秒一次性退避，不引入常驻轮询。超过预算则关闭、释放拦截并返回 input_interference；不持续弹窗与玩家争夺控制。

重复提交防护以 `operation ID + 稳定命令摘要` 为基础，不能以每次改变的 nonce 作为业务去重键。同一操作和同一内容再次提交只能返回已有状态；同一操作而内容不同必须拒绝。accepted 的记录先于业务分发建立，当前 runtime 内必须禁止再次调用同一业务。

**回执丢失不是未执行证明。** 没收到 accepted 时先查询同一接收事务/操作：只有受信状态明确证明未接受，才允许整帧重传；已经 accepted/running/reported 时继续取原结果。查询也失败、状态不完整或客户端已重载导致证据丢失时保持 unresolved，不自动补发执行。保留当前持久化 journal 和 reload 核验，不能仅靠 Lua 内存声称跨崩溃 exactly-once。

错误回执必须使用独立的最小编码路径，只含固定字段和短错误码；不能为了报告一份坏命令而再次编码同一个坏对象，重现报告编码失败后只剩超时的问题。

## 6. 组合键的宿主投递是独立验收门槛

**WoW 源码支持绑定与生产通道真机可靠投递须分别验收。**

原提案时发送器只实现 Return 与 WM_CHAR；工作区已增加专用组合键投递。Ctrl/Alt 涉及键盘状态和系统键消息语义，向 HWND 投递若干 WM_KEYDOWN/UP 不能直接当作真实修饰键状态已经改变。

独立 Retail 后台回显实验已两次观察到唤醒、ready、staged、accepted 和清屏；证据见[实验验收](../../tests/bridge-input/acceptance-2026-09-27.md)。该实验不是生产桥全链，也不覆盖其他布局或 Classic/Titan。正式路径仍要求新鲜 receiver_ready，不把首个 PostMessage 成功当作快捷键已触发。

必须先离线验证扫描码、左右修饰键、消息顺序、退出时释放、自有按键与玩家原有按键状态的边界，再另行做授权的客户端验收。背景窗口、已有普通输入焦点、中文输入法和非美式布局均是必测项；尤其已有 EditBox 可能优先消费唤醒键，此场景不可跳过。

若后台组合键不能可靠唤醒，不能发布“完全后台可靠”的承诺。需要明确选择另一个已验证的后台唤醒机制，或把受控前台原生 SendInput 作为产品模式变更。后者可由 Go CLI 自己完成、不需要 Computer Use，但会改变当前“不抢前台/不用 SendInput”的合同，不能作为静默兜底。本文未作此实现变更。

## 7. 与既有桥的关系

### 短回执与完整 SV 报告

```text
CLI 写入受管 Bridge/Definitions.lua 探针定义
  → prepare / reload 加载队列
  → load / run 执行已登记探针
  → 插件生成报告、发布二维码状态与校验回执
  → flush / reload 将完整报告写入 SavedVariables
  → CLI 读取 SV、关联并核验报告
  → ACK / finish 确认、退役队列条目并核验清屏
```

正常新探针链路保留加载与报告持久化两次 reload。当前文件名为 Definitions.lua，不是旧版 automation.lua；二维码回执不替代 SV 中的完整报告。当前原子 ACK/finish 不额外触发第三次清理 reload，清理确认也不代表又一次 SV 落盘。

二维码承担身份、握手、状态、摘要、最小错误、ACK 和清屏回执，业务结果正文统一使用 SV。本轮不建设无 reload 短脚本上传或完整光学结果分帧通道。保留已有“精确报告已落盘就直接核验”及原子 ACK 无清理 reload 的优化，不能为了统一流程多发 reload。

SV 内存更新不等于磁盘可读；当前完整报告仍通过 flush/reload 持久化。先完成采样、断言和探针资源清理，再保存同一报告。结果超限、编码失败、超时或回执丢失时不重跑探针，使用最小失败回执及精确报告恢复。二维码位置与绘制规则保持不变。

Skill 按已核验 product/build 查询固定 source/API 与插件源码，依据任务构建探针、声明执行预算、解释结果并调整实验。CLI 封装输入、恢复和 ACK/finish，Agent 不逐字符编排传输或停在二维码展示阶段。加载后重建测试场景；现有已加载能力无法采集重载前原现场时明确限制，不悄悄改变观察对象。详细要求见[总方案](bridge-refactor-plan-2026-09-27.md)。

### 执行预算

Agent 声明实验所需执行时长，随不可变请求保存。CLI 在输入前校验插件上限（当前异步 1..120 秒），插件回执确认接受的预算；超出支持范围明确拒绝，不静默截短。执行观察包含该预算和传输余量，加载、SV 持久化、ACK/显示清理另有预算，整体期限不能仍被固定 2 分钟截断。

接收硬期限及有界重传独立于实验时长，长探针不能延长模态占用。恢复沿用执行记录，不重置原执行预算或重跑；查询结果和清理可用新的有界恢复尝试。宿主超时、人工取消、插件执行超时分别记录，同步 Lua 仍不能靠宿主计时器抢占。

### 安装和失联时的独立兜底重载

固定流程为 `Esc → Esc → Esc → Enter → /reload → Enter`，是用户明确指定的安装激活/桥失联兜底，不要求桥、session、接收器或二维码预先可用。普通业务和正常可关联重载仍使用原有协议；此例外只发送固定 reload，不开放任意聊天命令。

首次发送前记录 reload attempt、目标窗口/进程、安装版本及输入进度，持有输入锁并逐条重核身份。每次尝试只发送一次；部分发送或结果未知先观察恢复，不循环清 Esc 和重载，也不绕过其他操作所有权。安装任务内部负责调用兜底、重新握手及版本核验，不把流程甩给 Agent 手动按键。

如果自有接收器仍在吞 Esc/Enter，先经已验证的 Ctrl+Alt+[ 关闭或不可续期的硬截止释放它，再执行固定序列；不要求先恢复 session 或收到正常回执。原型需专门验证此交接，避免把 `/reload` 发进协议 EditBox。

按键投递成功只代表已尝试。重载后必须核验新鲜身份、runtime 和目标版本；有旧 epoch 则核对变化，无旧 epoch 只声明首次激活证据。未获得确认则保留 pending，不伪造 nonce 关联、ACK 或加载成功。该固定 Esc 例外不授权普通通道清空其他输入。工作区命令为 `live reload fallback --installation <client> --pid <pid> --request <key> [--session <prior-session>]`；同一 `OP-...` 可由 `live status`/`live resume` 恢复观察，未知输入不得重发。

### 恢复与兼容边界

2026-09-27 15:39 调查增补：已有 identify 失败、reset 超时且没有 operation ID 的案例。因此首次唤醒前应创建独立 bootstrap attempt 证据，保存目标、阶段、输入进度和回执；没有 operation ID 不等于没有游戏输入。首次连接及恢复同样使用新接收器，不能只替换 run 的输入。

另一个 `panel absent` 案例来自 probe load 重载后临时界面消失，报告已成功传输并清理。专用接收框不消除队列加载的 reload 副作用；合同和 skill 必须明确 runtime 变化。重建场景由探针建立页面与前置条件；原现场无法用现有已加载能力采集时明确限制。本轮不把无 reload 新通道列入实施范围，两种观察不得混称。

专用窗口内部调用同一个经过校验的命令分发模块，不复制两套业务实现。identify/connect/reset/status/ACK 都通过专用接收通道获得机器输入，避免正常和恢复流程继续依赖聊天框。原 `/dev` 可以保留为用户工作台入口，但不能偷偷作为自动传输失败的兜底。

唤醒和身份查询本身不等于放弃旧操作。存在未决工作时，可以返回相同所有者的诊断/恢复状态，但不能借新接收框绕过锁、覆盖已有报告或重新执行探针。

新输入传输不能替代以下独立修复：

- 异步执行期限与 CLI 等待预算对齐。
- 编码失败、容量超限等产生最小、可编码的结构化失败回执。
- 已有操作结果可重新显示/读取，观察结果不依赖允许下一次输入。
- 超时、取消、未决、探针失败、业务断言未通过分别返回。

首版无需高频常驻轮询或全局键盘钩子。模态接收器首次打开才创建；关闭时卸载监听、取消计时器并释放临时数据；未连接时保留基础唤醒入口，不持有活动接收或调查资源。

## 8. 验收与实施顺序

1. **独立原型先行。** 在 `tests/bridge-input/` 创建测试插件及宿主脚本，复用 Go 原生输入/捕获模块；不覆盖受管生产安装。只回显事务、统计提交、记录 reload 启动标记，不执行业务探针。先验证无 session 唤醒/connect、组合键和固定 Esc×3/reload，再接入生产状态机与分发器。
2. **故障注入。** 在每个字符边界插入玩家字符（含合法 ASCII）、删除、替换、粘贴、截断、容量溢出；连续普通 Enter/Esc/鼠标操作、提前按提交键、staged 后输入、旧 nonce、旧字符和旧提交延迟到达、重复提交、CLI 退出、失焦、战斗/重载/角色变化。再覆盖 rejected/accepted/查询回执分别丢失、人工紧急取消和连续三次污染；断言无错误执行、无重复业务、重传严格有界、无永久拦截，普通通道不误清用户输入。兜底 Esc 的预期影响单独验收。
3. **客户端能力验收。** Retail/Classic/Titan 分别核对绑定、模态输入、后台快捷键和 protected/secret 边界。源码支持与真机成功分别记录。
4. **端到端恢复。** 正常 load/run/finish、运行中错误、回执隐藏、ACK 丢失和 reset；首次安装、旧桥失联的兜底重载、部分输入和未确认恢复；超过 15 秒及 120 秒执行加持久化余量。验证完整报告走 SV、无需 Computer Use，执行效果不确定时不重放。
5. **性能与体验。** 默认不展示协议长文本；正常提交马上解除模态，最长接收时限可见且可取消；基础唤醒注册单独计量，未启用调查功能零活动资源，无永久 OnUpdate、焦点争抢或全局输入封锁。

本方案的准确表述是“短时独占、可确认、可取消的机器命令接收器”，而不是“永远置顶、永远焦点、屏蔽所有动作”。后者在 CLI 故障和玩家紧急退出时反而会制造新的卡死。
