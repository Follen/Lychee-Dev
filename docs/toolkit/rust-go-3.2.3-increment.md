## Execution order and stopping conditions

1. Persist current documentation first. Map each changed Go test to an actual Rust regression, a justified platform exclusion, or an explicit uncovered item.
2. Implement the resource/capacity seam and all its real consumers coherently. A new Budget API alone does not satisfy admission ordering or query behavior. Keep necessary Windows calls behind minimal reviewed safe interfaces; do not introduce unsafe into business code.
3. Run local pure/Node checks first, then a meaningful exact-tree Windows batch for memory API and real CLI consumers. Keep failed runs and honest nonzero test counts; do not weaken limits to make a fixture pass.
4. Have independent Data/Skill users exercise real commands and recovery. Complete Source/Skill/Data quality loops and the five final sequential audits; this increment's review is not final convergence.
5. Compare cold/warm runtime and memory only at equivalent completed stages with equivalent results/checks. Rust controllable elapsed ≤30% Go remains unverified. An increased accounting ceiling or a failed process's lower sampled memory is not an optimization result.
